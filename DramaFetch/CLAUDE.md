# CLAUDE.md — DramaFetch

Rules for agents working in `DramaFetch/`. The repo-wide rules in `../AGENTS.md` and `../CLAUDE.md` (guardrails, branches, PRs) still apply; this file adds what is specific to this project. Read it before touching anything here.

## Scope — what this tool is and is not

- DramaFetch downloads TikTok short-drama episodes that the user's own account can already watch, a whole series at a time, for personal offline viewing. That is the whole product. The legal notice in `README.md` is part of the contract: keep it verbatim in the README, in `web/static/index.html` and in the Chrome extension (`legalNotice` in both `extension/_locales/*/messages.json` and the footer of `extension/src/app/app.html`; `extension/tests/locales.test.js` compares them with the README).
- Never implement anything that unlocks paid episodes, bypasses a paywall, DRM or access controls, fakes entitlement, rotates proxies or hides automation. The only two deliberate measures are a Chrome user agent without `Headless` (`static.chrome_user_agent`, used by the discovery and the browser engine alike) and curl_cffi's Chrome TLS impersonation (`impersonate="chrome"` in `static.py` and yt-dlp's `impersonate` in `downloader.py`), which is how yt-dlp normally talks to TikTok. Chromium runs with its default flags (`navigator.webdriver` stays true); when TikTok asks for a verification the user passes it with `--headful`. yt-dlp's TikTok extractor would solve TikTok's JS challenge on a video page itself (a proof of work it computes in Python, yt-dlp 2026.01.29 and later): `downloader.YtDlpChallengeGuard`, the `logger` of every yt-dlp run, stops it before the answer is computed or sent — `FAILED_BLOCKED`, a stop and the cooldown (`tests/test_downloader.py` drives the installed extractor over a stubbed challenge page). No proxies, no stealth plugins, nothing else. Locked episodes are listed with their hints and skipped; `--include-locked` only _asks_ for them, with the same session.
- Episodes the account has not unlocked are listed and skipped; paid episodes it has unlocked download like free ones; never unlock, never fake entitlement, never decrypt, never enable allow_unplayable_formats. What the session may play is decided by `catalog.access_of` from the payload TikTok served to the user's OWN session (`Episode.access`: `free`, `unlocked` — paid, and playable with that session: an entitlement flag, or a real play URL for a sold episode with no entitlement flag that says no — or `locked`), with that account's cookies; nothing is ever sent back to TikTok to change it — no payload field, no preview's or other account's URL, no re-signed or guessed URL. A priced episode without a play URL (a rendition without one, or a placeholder string, is none) or whose entitlement flag says no (`isUnlocked: false`) — and without an entitlement flag that says yes — is `locked` and never attempted unless `--include-locked`, which only asks, with the same session: TikTok decides. The same decision holds where a list is reused: the browser engine never adopts a fresh entry that reads as `locked` (`_refresh`, unless `--include-locked`), and the web's list cache serves a list only to the session that resolved it (`web.server.session_key`), so no download ever gets another session's access decision or signed URLs. Encrypted media is detected from the MP4 box structure (`media.drm_problem` / `drm_problem_in`) and never kept, `--no-verify` or not — nor adopted as the episode when a run finds it under the episode's name (`downloader.existing_file_result`, both engines and a run's stop) or a failed yt-dlp run left it there: deleted, `failed-unavailable`; the manifest remembers the verdict (`Manifest.drm_protected`), so the next run skips that episode without a request — only a DOWNLOAD's verdict (`models.DRM_MESSAGE` / `DRM_REMEMBERED_MESSAGE`): a payload's DRM flag, from the first list or a fresh one, is read again whenever the series is listed (a complete series is skipped for 24 hours: `--recheck`) and never remembered — and such an episode is left out of completeness like a locked one (`engine.series_report`). A payload DRM clue needs a key that names DRM in whole words (`catalog.is_drm_key`): precision over recall, because the media check is the real guard.
- Cookies are a key to the user's account: never print, log, dump, assert on or send cookie values anywhere but TikTok. Diagnostics (`doctor`, `--dump-raw`, error messages, job snapshots) may show cookie **names**, counts and ages only.
- Be polite to TikTok by design: one download at a time, randomized 4–9 s pauses between episodes, a 60–120 s rest every 10 downloads, 0.8–1.6 s between list pages, a full stop on HTTP 403, HTTP 429 or three failures in a row, and after any of those refusals (403, 429, a captcha) a 30-minute global cooldown — `cooldown.py`, one JSON file in `DRAMAFETCH_STATE_DIR` (default `~/.dramafetch/cooldown.json`) — during which `info`/`download`/`video` exit 5 and the web answers 429 without a single request (see Pacing below). Never add parallelism; never add a flag that skips the cooldown.
- Every saved video is verified before its cover step (`media.verify_video`: parses as an MP4, no top-level atom cut short, an audio track, a duration within `max(3 s, 5 %)` of the list's `Episode.duration_s`; the browser engine also fails a body shorter — or longer — than the announced `Content-Length` of an identity-encoded body, or a transfer the server cut off, without trying another mirror, and that transfer check is unconditional). A file that fails is renamed, not deleted: `media.quarantine` renames it `<stem> (incomplete).<ext>` (`(incomplete 2)`, …, never overwriting), the yt-dlp sidecar cover is deleted, no cover is fetched, and the episode is `FAILED` with `download looks incomplete or wrong: <reason> (kept as <name>)` (`media.INCOMPLETE_PREFIX`), so a rerun tries it again — the quarantined stem never matches `existing_episode_file`. The one exception: when the OS refuses the rename even after `media.RENAME_RETRIES` retries, `media.quarantine_note` deletes the file (`… (could not rename <name>: <error>; deleted, so that it does not pass for the episode)`; if not even that works, the note asks for a deletion by hand), because a bad file left under the episode's name would be skipped as done by the next run. `DownloadOptions.verify=False` / `--no-verify` skips the file check only (the Content-Length / aborted-transfer check is unconditional, and so is the DRM check, which runs before it and deletes an encrypted file instead of quarantining it — see the Scope bullet on paid episodes) and is documented as a debugging aid only; do not make verification conditional on anything else.
- One small cover (thumbnail) request per episode in the browser engine: one `GET` of `Episode.cover_url` after its video and only then, outside the media budget (`MAX_COVER_GETS = 1`), never retried, never a second candidate; its failure only appends `; cover: <reason>` to a `done` result (a 429 there is a WARNING, not a stop). The yt-dlp engine delegates the fetch to yt-dlp's `writethumbnail`, which gets the cover just before the video, names it after the cover URL's extension (`.jpeg` for TikTok) and reports nothing when it fails. By default (`DownloadOptions.thumbnail = "embed"`, `--thumbnail`) the cover then goes INTO the MP4 as its cover art — the `covr` atom, written by mutagen in `thumbnails.embed_cover` — and no sidecar stays; `both` keeps the sidecar too, `file` only the sidecar, `none` makes no cover request at all. Never modify a downloaded video in place: embedding edits a copy (`<name>.embed.part`) that replaces the original atomically, and any failure deletes the copy, leaves the video byte for byte and keeps the cover as a file (the message says so; the status never changes). A skipped episode never fetches a missing cover.
- The cloud sandbox and CI cannot reach tiktok.com — never try. Everything network-facing is thin, injectable and tested against `tests/fixtures/` or `tests/integration/fake_tiktok.py`.
- The web UI never serves a path outside `--out`: `GET /api/files/…` streams only the file a job row recorded — a `done` row, and `skipped-exists` rows are served too (a file an earlier run saved) — after resolving it inside `out_dir`, and answers a 404 that names no path to anything else; the save-all ZIP (`GET /api/files/<job>/all`, a finished job only) applies the same check to every entry, before answering and again right before opening each file, so the ZIP never includes a path outside `--out`. Binding `serve` to anything but loopback requires `--token` (or `DRAMAFETCH_TOKEN`; at least 8 cookie-safe characters), which every `/api/*` request must then carry as `Authorization: Bearer <token>` or the `dramafetch_session` cookie; the token value never appears in logs, messages or snapshots (`token: set` / `token: none`).

## The owner's acceptance criteria

What the owner asked DramaFetch to do. Every change keeps all eight true, and every maintenance agent (`download-guardian` and `vuln-sentinel` in the root `.claude/agents/`, `code-reviewer` and `test-runner` in `DramaFetch/.claude/agents/`) judges a change, an upstream release or a defect report against them — inside the Scope above, never against it:

1. **Whole series, in batches.** One link gets every episode the session may play; several links (`download URL [URL ...]`, `--from-file`, the web's "Several series" box, the extension's batch box) run strictly one series after the other — `engine.run_batch` / `run_series`, `extension/src/app/engine.js`. Proven by `tests/test_engine.py`, `tests/test_cli.py`, `tests/test_web.py` and the batch scenarios of `tests/integration/`.
2. **Files named `<Series name> - Episode NN`.** `models.DEFAULT_NAME_FORMAT = "{series} - Episode {number}"`, inside `<Series name> [<series id>]/`; the extension's `lib/naming.js` gives the same names (parity-tested) within Windows' path limits.
3. **Good audio and video, in sync.** The highest-bitrate rendition the account is served (`--quality compatible`: H.264; `best`: any codec), saved as served — nothing is ever re-encoded or remuxed — and every file verified (`media.verify_video` / `lib/mp4.verifyVideo`: parses, nothing cut short, an audio track, the listed duration within max(3 s, 5 %)).
4. **The JPG cover embedded in the MP4.** `--thumbnail embed` (the default) writes the `covr` atom on a copy that replaces the original atomically (`thumbnails.py`, `lib/mp4.embedCover`); the framemd5 proofs in `tests/test_extension_media.py` and integration `test_a` show no decoded frame or sample changes.
5. **Never trigger TikTok's anti-bot systems.** Behave like one person watching: the Pacing floors below, one request at a time, the 30-minute cooldown after a refusal, a full stop on a 429, a captcha, a login wall or 3 failures in a row — and nothing that hides automation (Scope).
6. **Paid episodes the account has unlocked, like Flixcam — nothing more.** `catalog.access_of` decides `free` / `unlocked` / `locked` from what TikTok served the user's own session; locked episodes are listed and skipped; DRM is detected and never decrypted or kept.
7. **A SnapAny-like page.** Paste a link, see the episodes with their covers, download all: `dramafetch serve` (the local web UI) and the Chrome extension's page — no terminal needed for the extension.
8. **Everything works.** The Definition of done below is green on every change; a skipped suite is "not run", never "passed"; what the sandbox cannot reach (TikTok) is verified on the owner's machine (`dramafetch doctor`, `--dump-raw`) before anyone claims it works there.

When an upstream project, a changelog, an issue or a web page shows a way to "fix" a download that would cross the Scope — solving or bypassing TikTok's challenges or captchas (yt-dlp's TikTok extractor does — DramaFetch stops it at one: `downloader.YtDlpChallengeGuard`; a yt-dlp release that changes how it meets them is tried against that guard's test before any floor moves), forging or generating request signatures or tokens, spoofing fingerprints or hiding automation, proxies or IP rotation, faster pacing, unlocking or faking entitlement, DRM keys or `allow_unplayable_formats` — it is never applied, here or in the extension. The agent reports what it saw and what it did not port.

## Pacing

The anti-bot strategy is to behave like one person watching, and it lives in `engine.download_series` with its knobs in `models.DownloadOptions`:

- The defaults are deliberate and are a floor: 4–9 s between episodes (`delay_min_s`/`delay_max_s`), a 60–120 s rest every 10 network attempts (`rest_every`, `rest_min_s`/`rest_max_s`; a failed attempt counts, skips do not), a stop after 3 consecutive failures (`max_consecutive_failures` — three failures in a row across the series of a run: the streak is `PacingState.consecutive_failures`, so it spans the series of a CLI batch and the jobs of the web; a `done`, a stop and an idle gap of `long_rest_min_s` reset it, a series boundary never does), at most 3 yt-dlp retries (`downloader.MAX_RETRIES`) with `sleep_interval_requests: 1`, at most 4 media requests per episode in the browser engine (`downloader_browser.MAX_GETS_PER_EPISODE`) plus at most one cover request (`MAX_COVER_GETS`). Never lower them in code, never make the code itself go below them, never make a pause conditional on "it worked last time". The existing flags accept lower values only so that tests against the fake server run fast; do not add further ways to go below the defaults. Users may raise them (`--pace human`, `--rest-every 5`, …); the only way to make a run lighter is fewer requests (`--engine browser`), never faster ones.
- Never parallelise: one download at a time in the engine, one job at a time in `web/jobs.py`, one browser context in the browser engine. No proxies, no rotation, no second instance.
- Batches (`engine.run_batch` for the CLI, `engine.run_series` per series — the web's batch jobs too) follow three rules that must never be weakened. **Never resolve the series of a batch up front**: each series is resolved right before its own downloads (all lists first would be a burst of page loads, and the signed play URLs would expire before their episodes are reached). **Never drop the series rest or the long break**: between two series that both contact TikTok the batch rests `rng.uniform(rest_min_s, rest_max_s)` (`on_pause("series-rest", s)`, through `run_series(before_network=…)`, before the next resolve and after the cooldown check — the first series, and one that makes no request, need none); across a whole RUN — one `engine.PacingState` for a CLI batch, one for the web job manager's lifetime — every `DownloadOptions.long_rest_every` (100) network attempts bring `"long-rest"`, `long_rest_min_s`–`long_rest_max_s` (15–30 min), in place of that step's pause (before the next resolve when it falls between two series of a CLI batch or two batch jobs of the web — `engine.long_rest_due` — never after it, where the fresh play URLs would wait through it), and an idle gap of `long_rest_min_s` counts as that break (the count restarts); no CLI flag sets any of the three, and none may be added. **Any stop ends the batch**: a `SeriesRun.stop` — a cooldown, a failed resolve (login, captcha, 429, any `DiscoveryError`), a stop status, a failure streak (also on the last episode, reported through `download_series(on_stop=…)`), a cooldown met right before an episode, a `cookies.txt` with malformed lines (`error_kind` `cookies`, `engine.COOKIES_STOP`, before the resolve: every download would refuse it) — makes every remaining series `not started: batch stopped in <name or id> (<reason>)` (`engine.not_started_message`) with no request at all, and `engine.check_cooldown()` is asked before every series and, inside `download_series`, before every network attempt. The complete skip (`models.RECHECK_AFTER_S` = 24 h) fires only for a whole-series run — no episodes spec (not even `all`), no `recheck` / `overwrite` / `include_locked` / `dry_run` — whose manifest (`engine.find_series_dir`: `iterdir` + `endswith(" [<id>]")`, never a glob; `manifest.read_manifest`: no side effects) says complete less than 24 h ago while every file it counted is still on disk (`Manifest.missing_files()` empty); never make it fire on anything weaker. Its report names the episodes the manifest recorded `skipped-locked` as locked (read-only, no rows) and its line then ends with `engine.RECHECK_HINT` (`unlocked more in the TikTok app since? --recheck looks again`). Every input of a CLI batch is parsed before the first request.
- `DownloadStatus.FAILED_BLOCKED` (HTTP 403 / forbidden / access denied from yt-dlp, and its `Your IP address is blocked from accessing this post` — TikTok's status 10204; a JS challenge on a video page, which `downloader.YtDlpChallengeGuard` stops unanswered — `downloader.CHALLENGE_STOPPED_MESSAGE`; a captcha page met by the browser engine's in-session list refresh) and `FAILED_RATE_LIMITED` (HTTP 429) stop the run, like `FAILED_LOGIN`: the remaining episodes get the same status with `stopped: …` and no request is made (`engine._STOP_STATUSES`); `exit_code` returns 5 for both. Do not retry, wait-and-knock or switch engines automatically after one — the user waits 30–60 minutes and resumes with the manifest. Keep `downloader.classify_error` mapping 403 wordings to `FAILED_BLOCKED` and `\b429\b` to `FAILED_RATE_LIMITED`, and keep the anti-bot rules first: login, then 429, then 403, and only then the DRM wording — a refusal that also names DRM is that refusal (a stop and, for 403 / 429, the cooldown), never a remembered DRM verdict. Both statuses also start the global cooldown (`engine.BLOCK_STATUSES` → `engine.record_block_if_refused` → `cooldown.record_block(message, source=options.engine)`, once per run, before the rest is marked `stopped`; `cli video` does the same for its one result), and so do a `RateLimitedError` or `ChallengeError` raised by the discovery inside `engine.resolve` (source `discovery`). Every path that contacts TikTok asks `engine.check_cooldown()` first — the CLI's `info`/`download`/`video` (`cli._refused_by_cooldown`: `error: <cooldown_message>` on stderr, exit 5, no request; `download --dry-run` still resolves the list, so it is refused too; `video --dry-run` needs no network and is exempt), the web's resolve/download — except the browser engine's in-session list refresh, which runs inside a download that already passed the check. `download_series` asks again right before every network attempt, after its pause: a cooldown another front end recorded meanwhile (during a long break, say) stops the run there — that episode and the rest `FAILED_RATE_LIMITED` with `stopped: cooldown until HH:MM`, `on_stop("cooldown until HH:MM")`, not recorded a second time. `COOLDOWN_MINUTES` is 30; do not lower it, do not add a flag that skips the cooldown (deleting the file is the documented, deliberate way to lift it).
- Every pause goes through `on_pause(kind, seconds)` then the injectable `sleep`; skips (manifest, a DRM verdict the manifest remembers, locked, existing file, dry run) never pause and never count. Tests use a fake `sleep` and a fixed `rng` — a test that really sleeps is a bug. A test never touches `~/.dramafetch`: `tests/conftest.py` sets `DRAMAFETCH_STATE_DIR` to `tmp_path` for every test (the autouse fixture `dramafetch_state_dir`, unit and integration alike; CLI subprocesses inherit it), so `cooldown.json` lands in the test's own directory.

## Architecture (`src/dramafetch/`)

| Module | Role |
| --- | --- |
| `models.py` | Dataclasses (`SeriesRef`, `VideoRef`, `Episode`, `Series`, options, `DownloadStatus`, `DownloadResult`) and the `Discovery` / `Downloader` protocols — pure data, shared by everything; `THUMBNAIL_MODES` (`embed` `both` `file` `none`) and `DownloadOptions.thumbnail` with its `thumbnails` / `embed_cover` / `keep_cover_file` properties; `QUALITY_MODES` (`compatible` `best`) and `DownloadOptions.quality` (default `compatible`), `DownloadOptions.verify` (default True), `Episode.quality_hint` (`"720p h264"`: the label of the rendition the default quality takes, None without one); `RECHECK_AFTER_S` (24 h: a series complete less recently than that is resolved again), `DownloadOptions.long_rest_every` / `long_rest_min_s` / `long_rest_max_s` (100 network attempts of a run, 900–1800 s: no CLI flag) and `DownloadOptions.recheck` (`--recheck`); `ACCESS_MODES` (`free` `unlocked` `locked`) and `Episode.access` / `paid` / `drm` (after `quality_hint`, before `raw`) — `access=""` derives `locked` from a non-empty `lock_hints` (or `drm`), else `free`, so a caller that sets only `lock_hints` keeps its build-6 meaning, and an access equal to that derivation follows later assignments of `lock_hints` / `drm` (also on a `dataclasses.replace` copy); a value outside `ACCESS_MODES`, or `drm` without `locked`, is a ValueError; `locked` is `access == "locked"`; `DRM_MARK` (`protected by DRM`: every DRM message starts with it), `DRM_MESSAGE` (`protected by DRM (encrypted tracks): DramaFetch does not decrypt it`: the verdict of a downloaded file, both engines, and of yt-dlp's own "DRM protected") and `DRM_REMEMBERED_MESSAGE` (`protected by DRM (found by an earlier run): DramaFetch does not decrypt it; --include-locked tries again`: the skip of a remembered verdict, written by `engine`) |
| `errors.py` | Exception hierarchy; each class maps to one CLI exit code — except `ThumbnailError`, which never escapes an engine (a cover that cannot be embedded is kept as a file and reported in the message), and `MediaError` (a saved file is not an MP4 mutagen can read), which `media.verify_video` turns into a reason |
| `media.py` | Integrity of a saved video, shared by both engines: `probe_video(path)` → `VideoProbe(duration_s, has_audio, audio_codec)` through mutagen (a video-only MP4 gives `has_audio=False`, never raises; a non-MP4 raises `MediaError`), `atom_problem(path)` (the top-level atom walk: a `KNOWN_ATOMS` member whose declared size runs past the end of the file → `truncated MP4 (<atom> atom cut short: <have> of <need> bytes)`; unknown atoms and trailing junk end the walk without a verdict), `verify_video(path, expected_duration_s)` → None or the reason (`not a valid MP4 (<detail>)`, the truncation, `no playable duration`, `no audio track`, `duration 61 s, expected 120 s` when `|actual − expected| > max(3.0, 0.05 × expected)`; suffixes outside `MP4_SUFFIXES` and a missing mutagen are not judged — the latter logs one WARNING and still walks the atoms), `quarantine(path, *, sleep)` → `<stem> (incomplete).<ext>` (`INCOMPLETE_MARK`, then ` (incomplete 2)`, …; a rename the OS refuses is retried `RENAME_RETRIES` (2) times, `RENAME_RETRY_DELAY_S` (0.5 s) apart, through the injectable `sleep`, then the `OSError` propagates), `quarantine_note(path)` → the parenthesised end of the engines' FAILED message: `kept as <name>`, or — the rename refused for good — `could not rename <name>: <error>; deleted, so that it does not pass for the episode` (the file is deleted, the one case in which a download is; WARNING logged), or `could not rename or delete <name>: <error> — delete it by hand, or the next run skips the episode as already downloaded`, `INCOMPLETE_PREFIX` = `download looks incomplete or wrong: `; the DRM check, which ALWAYS runs (`--no-verify` or not): `drm_problem(path)` and `drm_problem_in(data)` (a body still in memory) walk the box STRUCTURE — box headers only, never the samples: the top-level boxes, the `moov` children (`pssh`), the `moov/trak/mdia/minf/stbl/stsd` sample entries (`encv` / `enca`, `ENCRYPTED_SAMPLE_ENTRIES`) and a top-level `pssh` (`PSSH_BOX`) — bounded (`_MAX_DRM_BOXES`) and never raising (a malformed file is "no DRM found"; the integrity check judges it), never a raw byte search (`encv` inside `mdat` means nothing) → `models.DRM_MESSAGE` or None; `discard(path, *, sleep)` / `discard_note(path, *, sleep)` delete an encrypted file — never quarantined: no rerun makes it play — retried like a rename, the note `could not delete <name>: … — delete it by hand …` when the OS refuses |
| `cooldown.py` | The global "do not contact TikTok" window after a refusal: `COOLDOWN_MINUTES` (30), `STATE_DIR_ENV` (`DRAMAFETCH_STATE_DIR`, default `~/.dramafetch`), `Cooldown(until, reason, source, recorded_at=None)` with `seconds_left` / `minutes_left` / `active` / `started`, `record_block(reason, source, *, now, minutes)` (atomic write of `{"until", "reason", "source", "recorded_at"}` to `cooldown.json`; a newer refusal restarts the window; an unwritable directory is logged, never raised), `active_cooldown(*, now)` → the cooldown in force or None (never raises: missing, unreadable or corrupt file = no cooldown), `read_cooldown`, `clear_cooldown`, `cooldown_message` (`TikTok refused a request at HH:MM (<reason>); DramaFetch waits until HH:MM (N min left) before contacting TikTok again — delete <path> to lift it, at your own risk`), `cooldown_summary` (`until HH:MM (N min left): <reason>`, the `doctor` line), `clock_time`, `state_dir`, `cooldown_path`. Reasons are already-sanitised engine messages, whitespace-collapsed and cut at 200 characters; no cookie value can reach the file |
| `urls.py` | Parse pasted text into `SeriesRef` / `VideoRef`, build page URLs; its docstring holds the verified URL facts; ids and episode numbers are ASCII `[0-9]`, never `\d` (full-width or Arabic-Indic digits are refused like any unsupported text) |
| `catalog.py` | Pure functions over TikTok's `item_list` / `detail` payloads: find lists, lock hints, episodes, merge, warnings, the cover URL (`cover_url_of`: `video.originCover` → `cover` → `dynamicCover`, each a string, a list or a `UrlList` dict), and the renditions: `renditions(item)` → `Rendition(url_list, codec, bitrate, height_hint, label)` per `video.bitrateInfo` entry with a play URL (`codec_name`: `h264` / `h265` / `bytevc1` / lower-cased raw / `unknown`; the height from the `GearName` — `normal_720_0`, `adapt_lower_1080_1` — else `video.ratio`, else `?p`; `label` like `720p h264`), `ordered_renditions(item, quality)` / `choose_rendition(item, quality)` (`compatible`: the H.264 ones by bitrate descending, then the rest — so the top H.264, or the top of anything when no H.264 is listed; `best`: all by bitrate descending), `play_url_candidates(item, quality="compatible")` (the renditions' URLs in that order, then `video.playAddr`, de-duplicated) and `url_expiry`; `episode_from_item` fills `Episode.quality_hint` from the compatible rendition; `access_of(item)` → `(access, paid, drm, hints)`, pure, deterministic, never raising on junk: it scans the item's top-level scalars (an `itemStruct` wrapper's too, the outer key winning), `dramaInfo` recursively (`MAX_DEPTH`) and `video`'s top-level scalars, keys case-insensitive, into DRM (`is_drm_key(key)`: one of its `key_words(key)` — camelCase, PascalCase with its acronym runs (`DRMType` → `drm`, `type`; `HDRBit` → `hdr`, `bit`) and their plurals (`encryptedIDs` → `encrypted`, `ids`), snake_case, kebab-case, digits — is `drm` or starts with `encrypt`, and none is a negation (`free` `no` `non` `not` `un` `without`) or an identifier (`id` `ids` `uid` `uids`); truthy — so never `hdrMode`, `isDrmFree`, `no_drm`, `nonEncrypted`, `unencrypted`, `unEncrypted`, `encryptedUid` or `encryptedUIDs`: a DRM clue locks whatever else the payload says and only saves a download the media check would refuse, so precision beats recall), ENTITLED (the full key `(is_?)?(unlocked|purchased|bought|entitled)`, `has_?(paid|purchased|unlocked|bought|access)` or `paid_?by_?(user|viewer|me)`, truthy; an `(unlock|pay|purchase)_?status` or `lock_?status` string `unlocked` / `paid` / `purchased` / `bought` / `entitled`), NOT-ENTITLED (one of those full keys with a falsy value — `isUnlocked: false`, `hasPaid: 0` — hint `<key>=<value>`, not counted in `paid`; `series_to_dict` carries `access` / `paid` / `drm` (with `locked` and `lock_hints`: the badges) and `on_disk` per episode and `on_disk_count` (`on_disk_numbers(out_dir, series_id, series_dir(out_dir, series))` → `engine.on_disk_numbers`: the manifest of the folder a download would use, `manifest.read_manifest`, read-only, never raises)), `jobs.py` (`JobManager`: ONE worker thread runs one job at a time, FIFO; a download job holds a resolved `Series` + episodes, a batch job only its `SeriesRef`, resolved lazily by the series runner in the worker; ONE `engine.PacingState` for the manager's lifetime (`pacing`: the long break and the failure streak span jobs), handed to every run with its injectable `sleep` / `clock` / `rng`; the rest between jobs — `before_network()`, called by `run_series` right before resolving and by `GuardedDownloader` before every episode that may contact TikTok: the job's first call rests `rng.uniform(rest_min_s, rest_max_s)` (`"job-rest"` in the snapshot's `pause`) when the last job that contacted TikTok finished at most `rest_max_s` ago — for a batch job, whose first call comes right before its resolve, the long break instead when `engine.long_rest_due` says it is due (`"long-rest"`, `long_rest_min_s`–`long_rest_max_s`, the count started again; a download job leaves it to `download_series`) — then asks the gate again (`JobRefused` ends the job before its request); a job that makes no request — a series skipped as complete, a download job whose episodes are all on disk — takes no rest, but a batch job counts as contacting TikTok from its resolve on, even when the list then comes from the 15-minute cache; a stop — `SeriesRun.stop`, a stop reported by `download_series`'s `on_stop` (`note_stop`) or found in the rows, a gate refusal — cancels every queued job: state `cancelled` (finished), `error` `not started: batch stopped in <name> (<reason>)`, no request; snapshots carry `batch_id`, `series_name` (from `on_start` once resolved), `total`, `report` (`engine.report_to_dict` with its `line`, null until the job ends; a download job's over `engine.report_rows`, so **Download selected** / **Download all available** report on the whole series), `pause`, `counts`, `processed`, `files`; `summaries()` is the list without rows, most recent first, at most `MAX_LISTED_JOBS` (100); rows carry `path`, `file_name` and `thumbnail` — "a cover is available", as a sidecar or embedded (`has_cover`), computed once when the row is recorded, never on a poll; its `gate` — `DramaFetchServer.job_refusal` — is asked when a job reaches the front of the queue (a job is `running` only once it passed) and ends it as `error` with the cooldown message, no request made, when TikTok refused a request meanwhile), `static/index.html` (vanilla JS, no CDN: covers, the `free` / `paid · unlocked` / `locked` badges (`episodeAccess`, `accessBadge`: unlocked episodes ticked like free ones, locked ones unticked with their hints) and **on disk** badges, **Download all available** (the free and unlocked episodes, `availableNumbers`), **Save video** / **Cover** links — the embedded or the saved cover — for `done` and `skipped-exists` rows, the **Several series** box (one link per line, `--from-file` rules, **Queue all** → `POST /api/batch`), the **Jobs** panel (`GET /api/jobs` every 2 s while a job is queued or running: name, state, done/total, `complete` / `incomplete` badge and line from `report`, **Save all (ZIP)**, **Details** → the results table, above which **Save all (ZIP)** shows too), the token form shown on a 401 of kind `auth`, the **Refresh list** link next to the resolved title, and on a 429 of kind `cooldown` the message with the minutes left counted down locally from `Retry-After` while the download and Queue all buttons stay disabled) |

Dependencies flow downwards: `cli` / `web` → `engine` → `discovery` / `downloader` / `downloader_browser` / `manifest` / `catalog` → `thumbnails` and `media` (`thumbnails` imports `errors` only, `media` `errors` and `models` — for `DRM_MESSAGE`; both import mutagen lazily; `web` uses `thumbnails` too) → `models` / `urls` / `errors`; `cooldown` is stdlib-only and imported by `engine` (recording, `check_cooldown`), `cli` (the messages) and `web` (the 429 answer). `engine` imports `downloader_browser` lazily (`make_downloader`), so the default engine never loads Playwright. `web` imports `engine` and `cli` lazily inside handlers so the package loads without Playwright or yt-dlp; `cli` imports `web.server` lazily for `serve` (the `--token`/`--host` checks and `run_server`).

## Extension (`extension/`)

DramaFetch for Chrome is a second front end — a Manifest V3 extension for users without Python (Windows first) — that re-implements the engine in plain ES2022 modules: `// @ts-check` and JSDoc types in every file, no npm dependency at all (Node built-ins only in its tests), no CDN or remote resource. The Python package is not touched by it. The Scope and Pacing sections above bind it exactly as they bind the Python tool; the parity test (`tests/test_extension_parity.py`, `tests/test_extension_media.py`) proves its texts, constants and decisions equal the Python ones.

- **The line.** Only what TikTok serves to the user's OWN logged-in Chrome session. Never unlock, buy, fake or claim entitlement, send a payload field back, reuse a preview's or another account's URL, re-sign or guess a URL, or decrypt/strip DRM; encrypted media is never saved. No stealth, no tampering: never patch, wrap or override anything in TikTok's page (no fetch/XHR monkeypatching, no navigator/UA spoofing), never `chrome.debugger`, never read cookies (the page's own requests carry the session), never change a request of TikTok's page. Its only header changes are on its OWN media, cover and thumbnail requests — `Referer: https://www.tiktok.com/` set and `Origin` removed, what the Python browser engine's Playwright request and yt-dlp send — through one declarativeNetRequest SESSION rule whose `initiatorDomains` is the extension itself (`downloader.refererRule` / `applyRefererRule`: `requestDomains` = `TIKTOK_DOMAINS` in production, a `urlFilter` on the test origin in test mode). Those requests go out with `redirect: "manual"`; a redirect is followed only through `redirects.fetchFollowing` (see the permissions bullet). The discovery observes the series tab's requests with `chrome.webRequest` (URLs and status codes only, never bodies, never blocking), the app page observes `onBeforeRedirect` for its own requests (`src/app/redirects.js`: the target URL only, registered for the DramaFetch tab only, filtered to the host permissions, to the extension's own initiator and to the current request of each URL), and the discovery fetches the list pages with `chrome.scripting.executeScript({world: "MAIN"})` running the page's own `fetch` (`discovery.fetchInPage`, the port of `browser.FETCH_JS`); scrolling and the captcha check run in the ISOLATED world. One request at a time, one job at a time (a Web Lock makes one app tab per browser the engine), never every list of a batch up front.
- **The permissions are a contract** (`extension/tests/manifest.test.js` asserts them): `downloads`, `storage`, `scripting`, `tabs`, `webRequest`, `declarativeNetRequestWithHostAccess`; host permissions `https://www.tiktok.com/*`, `https://*.tiktok.com/*`, `https://*.tiktokcdn.com/*`, `https://*.tiktokcdn-us.com/*`, `https://*.tiktokcdn-eu.com/*`, `https://*.tiktokv.com/*`, `https://*.tiktokv.us/*`, `https://*.byteoversea.com/*`, `https://*.ibytedtos.com/*`, `https://*.ibyteimg.com/*`, `https://*.muscdn.com/*` — never `cookies`, `debugger`, `<all_urls>`, blocking webRequest or remote code; the CSP is `script-src 'self'; object-src 'self'`. A media, cover or thumbnail URL whose host the manifest does not cover is never requested (`downloader.hostCovered`), nor any redirect target outside the header rule's scope (`downloader.redirectTargetAllowed`: `TIKTOK_DOMAINS` in production, the test origin in test mode; https never downgraded, no loop, at most `MAX_REDIRECTS` = 5 hops — `redirects.fetchFollowing`; a target outside that scope counts like a refused URL, while a loop or a sixth hop fails the episode like Playwright's raised request); `TIKTOK_DOMAINS` equals the manifest's host-permission domains exactly (`tests/network.test.js`). Adding a permission needs a human decision and a README line saying why.
- **Test mode.** Overrides — another base URL than TikTok's, pacing below the floors, short discovery timeouts — are honoured ONLY when `chrome.runtime.getManifest().dramafetch_test === true` (`storage.isTestMode`; `loadTestSettings` returns `{}` otherwise and `saveTestSettings` refuses). The shipped `manifest.json` never has that key nor any localhost / 127.0.0.1 permission: `tests/integration/extension_harness.py` adds both to a temporary COPY. Outside test mode the settings refuse any pause below the Python defaults (`lib/pacing.pacingProblem`): users may only raise them; the long break and `maxConsecutiveFailures` have no user setting. In any mode a pause over `MAX_PAUSE_S` (86400 s, one day) is refused, and every pause is slept to its deadline (`lib/pacing.sleepSeconds`: timers of at most `MAX_TIMER_MS` re-armed until then, an `AbortSignal` for **Stop**), so it can only come out longer.

## Conventions

- English everywhere; conventional commits (`feat(dramafetch): …`, `fix(dramafetch): …`).
- Type hints on everything and `mypy --strict` green; `typing.Any` only for raw TikTok JSON. No `# type: ignore` without a reason in the comment.
- Parsing is pure functions over payloads, covered by the fixtures in `tests/fixtures/` (two consecutive `item_list` pages with a trailer, a duplicate, a locked episode and an item from another series; `item_list_series2.json`, the one page of the fake TikTok's second series — "Second Chance Bride", `7699393770256782399`, three free episodes, TikTok announces 3; `item_list_series3_logged_in.json` / `item_list_series3_logged_out.json`, the fake TikTok's third series — "Paid Love Story", `7699393770256782388`, four episodes, TikTok announces 4 — as the session of the account that bought episode 3 sees it (1-2 free; 3 `isFree: false`, `unlockPrice: 30`, `isUnlocked: true` with play URLs; 4 `isLocked: true` in `dramaInfo` and at the top level, no play URLs) and as a session without the `sessionid` cookie sees it (3 `isLocked: true`, no play URLs)). Keep fixtures realistic when extending them.
- The network layer is thin and injectable: the `Discovery` / `Downloader` protocols, the `fetch` / `playwright_factory` / `ydl_factory` constructor hooks, `DiscoveryOptions.base_url` for the fake server. Tests inject fakes; no test opens a socket to the internet.
- No new runtime dependencies beyond `yt-dlp`, `playwright` and `mutagen` (pure Python; it writes the cover into the MP4 — `curl_cffi` is an optional extra). Stdlib only under `web/`; no CDN or external resource in `index.html`.
- Never weaken `pyproject.toml` (ruff rules, mypy strict, pytest markers/addopts) to get green; never skip or quarantine a test.
- A test never touches `~/.dramafetch`: set `DRAMAFETCH_STATE_DIR` to `tmp_path` — `tests/conftest.py` already does it for every test through the autouse `dramafetch_state_dir` fixture — and never sleeps for real, binds a non-loopback address or reaches tiktok.com. The fake CDN's lists say `duration: 3` (what `tiny.mp4` lasts) unless `short_media`; `truncate_media` cuts the body at 60 % of the announced `Content-Length`; `gzip_media` serves it `Content-Encoding: gzip` with the compressed size as `Content-Length` (the decoded body is longer than announced: not a truncation); `drm_media` (a set of `(series id, episode number)`) serves the encrypted variant of `tiny.mp4` that `tests/encrypted_mp4.py` builds by a structural edit (`encv` / `enca` sample entries, a `pssh` box — nothing really encrypted, no binary fixture); the third series' lists depend on the `sessionid` cookie (`logged_in`; its value is never stored). For the extension's own requests: `redirect_media` / `redirect_covers` answer a 302 to a host the test copy does not cover (`localhost`, seen in `elsewhere_requests`); `media_hops` / `cover_hops` a same-origin 302 chain `/hop/1/…` … `/hop/<n>/…` (`hop_requests`), whose last hop `hops_then_elsewhere` sends to `localhost`; `origin_probe` answers `POST /origin-probe` with 204 (`probe_requests`); `cookie_control` serves a third-party cookie control (`/cookie-control/…`, `control_requests`). The request log keeps the `Origin` and `Referer` values and the header NAMES — never another header's value, never a cookie value — and no answer carries a CORS header.
- Error messages are safe to print: no cookies, no tokens, no tracebacks in user-facing text (`logging.debug` the detail). Web responses never echo request bodies.

## Definition of done

1. `ruff check`, `ruff format --check`, `mypy` and `pytest` are green; `pytest -m integration` too when a Chromium is available; and, from `extension/`, `node --test` and the `tsc` check. Report the real output.
2. Anything users see — flags, exit codes, output layout, statuses, API routes, pacing defaults — is reflected in `README.md` (flags table, exit codes, "Pacing and TikTok's protections"); a new or moved module appears in the table above.
3. No cookie value anywhere, no bypass of any kind, no parallel downloads, no new dependencies.
4. Fixtures and `tests/integration/fake_tiktok.py` were updated whenever TikTok's payload shape changed.

## Agents

Four agents maintain DramaFetch. Each judges a change, an upstream release or a defect report against the Scope and the owner's acceptance criteria above, and none commits, pushes or merges — the shift (or `repo-steward`) commits and pushes under the repository's branch and PR rules, and a human merges (or `merge-steward`, for a PR that passes the merge gate).

| Agent | Where | Does |
| --- | --- | --- |
| `download-guardian` | `../.claude/agents/` | Keeps the downloads meeting the criteria: runs `../.claude/scripts/dramafetch-watch.sh` and the definition of done (`DRAMAFETCH_REQUIRE_TOOLS=1`; in the nightly shift it takes the shift's results instead of running it again), reads what changed upstream — yt-dlp's TikTok extractor and changelog, Playwright, mutagen, curl_cffi, Chrome's extension platform — from primary sources only, and ships the smallest cited fix in both front ends; majors, new permissions and indirect evidence become issues. The DramaFetch steps of the nightly maintenance shift |
| `vuln-sentinel` | `../.claude/agents/` | Read-only vulnerability watch: every installed distribution against PyPI's per-version OSV data, yt-dlp's security notes, the extension's permissions, CSP and message handling, the web UI's token, Host guard and `--out` confinement, committed cookie values, the `dramafetch` CI job. The DramaFetch part of the weekly security review |
| `code-reviewer` | `.claude/agents/` | Read-only review of every DramaFetch diff against the Scope, the criteria, the pacing floors, privacy, Python–extension parity and cited TikTok facts, before every DramaFetch PR |
| `test-runner` | `.claude/agents/` | Runs the definition of done (`haiku`) and reports the counts and only the failures; a skipped suite is "not run" |

A DramaFetch pull request reaches `main` only through the merge gate (`../.claude/shifts/merge-gate.md`) or a human: the gate runs this whole definition of done itself with `DRAMAFETCH_REQUIRE_TOOLS=1` (integration included) on the PR merged into `main`, refuses a PR whose suites lost tests, and needs an independent review of code changes and `download-guardian`'s verdict on a yt-dlp, Playwright, curl_cffi or mutagen bump. It never merges a change to the Scope, the acceptance criteria, the legal notice, the extension's permissions or a download rule (pacing, cooldown, retries, `YtDlpChallengeGuard`): those wait for the owner.

The upstream watch is `tools/upstream_watch.py` (standard library only; covered by `ruff` and `mypy` and by `tests/test_upstream_watch.py`), run through `../.claude/scripts/dramafetch-watch.sh`: PyPI's JSON API (the latest releases, and each installed version's vulnerabilities from OSV), yt-dlp's raw `Changelog.md` and `yt_dlp/extractor/tiktok.py` at the installed release's git tag (`yt_dlp.version.__version__` of the inspected interpreter — PyPI's `2026.8.19` is the tag `2026.08.19`; `tag_of` pads the version the same way when that cannot be read) and at `master` (with the names DramaFetch reads in TikTok's payload — the literals of `catalog.py`, `discovery/browser.py` and `urls.py` — that the extractor stopped or started quoting), and Chrome Stable from Google's version history API next to the extension's `minimum_chrome_version`. Whatever it could not check — a source that did not answer, a direct dependency not installed or not checked, the extractor not compared, Chrome Stable not read — is an Attention item too, so `nothing new` means everything was compared. It never contacts TikTok; its report is evidence for an agent, never a decision, and nothing found upstream moves the line drawn in the Scope. From the repository root, where a session lists only the root agents, the shifts run `code-reviewer` and `test-runner` as a `general-purpose` subagent that follows the agent's file.

## Where the TikTok facts live and how to update them

The verified facts — the series URL shape, "the long number is the series id (`dramaID`)", `/api/drama/episode/item_list/`, `/api/drama/detail/`, "a logged-in session is required", yt-dlp issue #17725 — are written down in `urls.py` (module docstring) and `README.md` → "How it works", and encoded in `catalog.py` (field names, the access heuristics of `access_of`: free / unlocked / locked) and `discovery/browser.py` (URL substrings, pagination parameters). When TikTok changes something:

1. On a real machine run `dramafetch info URL --cookies cookies.txt --strategy browser --dump-raw raw/`; it writes `item_list_<n>.json`, `detail.json` and `page_url.txt` (never cookies). With `--strategy auto` or `static` the embedded page JSON lands in `hydration_<n>.json` instead, and `item_list_<n>.json`/`detail.json` appear only if the browser had to run.
2. Compare them with `tests/fixtures/item_list_page*.json`; update the fixtures to the new shape (anonymise ids) and adjust `catalog.py` / `discovery/` until `pytest` passes again.
3. Update the facts in `urls.py`, `README.md` and this file in the same PR, with the date they were verified.
