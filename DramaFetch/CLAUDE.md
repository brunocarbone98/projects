# CLAUDE.md — DramaFetch

Rules for agents working in `DramaFetch/`. The repo-wide rules in `../AGENTS.md` and `../CLAUDE.md` (guardrails, branches, PRs) still apply; this file adds what is specific to this project. Read it before touching anything here.

## Scope — what this tool is and is not

- DramaFetch downloads TikTok short-drama episodes that the user's own account can already watch, a whole series at a time, for personal offline viewing. That is the whole product. The legal notice in `README.md` is part of the contract: keep it verbatim in the README, in `web/static/index.html` and in the Chrome extension (`legalNotice` in both `extension/_locales/*/messages.json` and the footer of `extension/src/app/app.html`; `extension/tests/locales.test.js` compares them with the README).
- Never implement anything that unlocks paid episodes, bypasses a paywall, DRM or access controls, fakes entitlement, rotates proxies or hides automation. The only two deliberate measures are a Chrome user agent without `Headless` — `static.chrome_user_agent`: the Playwright contexts of the discovery and the browser engine and the static strategy's urllib fallback use it; with curl_cffi the static request carries curl_cffi's own Chrome header set instead (`static.IMPERSONATED_HEADERS`: DramaFetch's `User-Agent`, `Accept` and `Accept-Language` are left out so that the headers agree with the impersonated TLS fingerprint and client hints — a `Chrome/153` user agent next to `sec-ch-ua: "Google Chrome";v="152"` was a contradiction; the `Cookie` header stays DramaFetch's) — and curl_cffi's Chrome TLS impersonation (`impersonate="chrome"` in `static.py` and yt-dlp's `impersonate` in `downloader.py`), which is how yt-dlp normally talks to TikTok. For the user agent measure to hold at all, both Chromium launch sites (`discovery/browser.py` `_launch`, `downloader_browser.py` `_open`) pass Playwright's channel `chromium` (`static.DEFAULT_BROWSER_CHANNEL`) when neither `--browser-path` nor `--browser-channel` is given: the FULL Chromium runs headless, never Playwright's `chromium-headless-shell` — its default for a headless launch since Playwright 1.49 — which announces `HeadlessChrome` in `Sec-CH-UA` and `navigator.userAgentData` whatever user agent the context sets; `--browser-channel chrome|msedge` launches the installed browser. Chromium runs with its default flags (`navigator.webdriver` stays true) and the machine's locale (the contexts set no `locale`); when TikTok asks for a verification the user passes it with `--headful`. The `tiktok` extractor arguments `app_info`, `device_id` and `api_hostname` are refused (`cli.REFUSED_EXTRACTOR_ARGS`, a usage error, exit 2): each makes yt-dlp call TikTok's mobile API as an invented Android device (random device and install ids, a Pixel identity, an app user agent), a fingerprint DramaFetch never presents. yt-dlp's TikTok extractor would solve TikTok's JS challenge on a video page itself (a proof of work it computes in Python, yt-dlp 2026.01.29 and later): `downloader.YtDlpChallengeGuard`, the `logger` of every yt-dlp run, stops it before the answer is computed or sent — `FAILED_BLOCKED`, a stop and the cooldown (`tests/test_downloader.py` drives the installed extractor over a stubbed challenge page). No proxies, no stealth plugins, nothing else. Locked episodes are listed with their hints and skipped; `--include-locked` only _asks_ for them, with the same session.
- Episodes the account has not unlocked are listed and skipped; paid episodes it has unlocked download like free ones; never unlock, never fake entitlement, never decrypt, never enable allow_unplayable_formats. What the session may play is decided by `catalog.access_of` from the payload TikTok served to the user's OWN session (`Episode.access`: `free`, `unlocked` — paid, and playable with that session: an entitlement flag, or a real play URL for a sold episode with no entitlement flag that says no — or `locked`), with that account's cookies; nothing is ever sent back to TikTok to change it — no payload field, no preview's or other account's URL, no re-signed or guessed URL. A priced episode without a play URL (a rendition without one, or a placeholder string, is none) or whose entitlement flag says no (`isUnlocked: false`) — and without an entitlement flag that says yes — is `locked` and never attempted unless `--include-locked`, which only asks, with the same session: TikTok decides. Verified 2026-11-06 on the owner's real run (62 items of a free series with conditions): `dramaInfo.isLimitedFree: true` makes the series `free` whatever price it names (the FREE class beats PRICING); `DramaVideoData.IsFreeIntro` ("is this the free intro teaser", false on every episode), `IsPreview` and `PreviewType` sit on fully served episodes and give no clue and no hint — `preview` and `trial` are no lock words any more, and a `free` key with `intro` among its words is no clue; what tells a short-served episode apart is the SHORT-HEADER rule, structural and before any request: `music.duration` (the episode's own sound, `music.original` truthy) at most `SHORT_HEADER_RATIO` (0.85) of `video.duration` and at least `SHORT_HEADER_MIN_GAP_S` (1 s) shorter → `locked` with the hint `plays 69 s of 106 s` (`catalog.SHORT_HEADER_HINT_PREFIX`). When TikTok serves such a file anyway — the whole episode by size, within `downloader.SHORT_SIZE_TOLERANCE` (0.5 %) of a size the list announced (`catalog.listed_sizes`: `video.size`, every `PlayAddr.DataSize`), with a header that plays less — both engines name it (`downloader.served_short`, `models.SHORT_SERVED_PREFIX`: `TikTok serves this episode short: the whole file came (<size> bytes, as listed) but it plays <a> s of <e> s — if the TikTok app plays it whole, watch it there, then --recheck looks again; if the app breaks at the same point, the episode is defective on TikTok's side and no retry changes it`, `FAILED_UNAVAILABLE`, the Python file kept as `(short)`, the extension saving nothing) and never rewrite the header to play past what it indexes — such a file is a window for an episode the account has not unlocked, or a defective encode on TikTok's side (the owner's 7 episodes of 2026-11-06 broke at the same point in the TikTok app and in TikTok's web player: no sound past it, a broken picture when seeking past it), and the list cannot tell the two apart, so every text names what was measured and offers both readings; the manifest does not remember it (the next listing's SHORT-HEADER rule decides). The same decision holds where a list is reused: the browser engine never adopts a fresh entry that reads as `locked` (`_refresh`, unless `--include-locked`), and the web's list cache serves a list only to the session that resolved it (`web.server.session_key`), so no download ever gets another session's access decision or signed URLs. Encrypted media is detected from the MP4 box structure (`media.drm_problem` / `drm_problem_in`) and never kept, `--no-verify` or not — nor adopted as the episode when a run finds it under the episode's name (`downloader.existing_file_result`, both engines and a run's stop) or a failed yt-dlp run left it there: deleted, `failed-unavailable`; the manifest remembers the verdict (`Manifest.drm_protected`), so the next run skips that episode without a request — only a DOWNLOAD's verdict (`models.DRM_MESSAGE` / `DRM_REMEMBERED_MESSAGE`): a payload's DRM flag, from the first list or a fresh one, is read again whenever the series is listed (a complete series is skipped for 24 hours: `--recheck`) and never remembered — and such an episode is left out of completeness like a locked one (`engine.series_report`). A payload DRM clue needs a key that names DRM in whole words (`catalog.is_drm_key`): precision over recall, because the media check is the real guard.
- Cookies are a key to the user's account: never print, log, dump, assert on or send cookie values anywhere but TikTok. Diagnostics (`doctor`, `--dump-raw`, error messages, job snapshots) may show cookie **names**, counts and ages only.
- Be polite to TikTok by design: one download at a time, randomized 4–9 s pauses between episodes, a 60–120 s rest every 10 downloads, 0.8–1.6 s between list pages, a full stop on HTTP 403, HTTP 429 or three failures in a row, and after any of those refusals (403, 429, a captcha) a 30-minute global cooldown — `cooldown.py`, one JSON file in `DRAMAFETCH_STATE_DIR` (default `~/.dramafetch/cooldown.json`) — during which `info`/`download`/`video` exit 5 and the web answers 429 without a single request (see Pacing below). Never add parallelism; never add a flag that skips the cooldown.
- Every saved video is verified before its cover step (`media.verify_video`: parses as an MP4, no top-level atom cut short, an audio track, a duration within `max(3 s, 5 %)` of the list's `Episode.duration_s`; the browser engine also fails a body shorter — or longer — than the announced `Content-Length` of an identity-encoded body, or a transfer the server cut off, without trying another mirror, and that transfer check is unconditional). A file that fails is renamed, not deleted: `media.quarantine` renames it `<stem> (incomplete).<ext>` (`(incomplete 2)`, …, never overwriting), the yt-dlp sidecar cover is deleted, no cover is fetched, and the episode is `FAILED` with `download looks incomplete or wrong: <reason> (kept as <name>)` (`media.INCOMPLETE_PREFIX`), so a rerun tries it again — the quarantined stem never matches `existing_episode_file`; a file that fails only the duration, plays LESS and is the whole episode by size (`downloader.served_short`) is short-served instead: renamed `<stem> (short).<ext>` (`media.quarantine(…, mark=SHORT_MARK)`), `FAILED_UNAVAILABLE` with the short-served message and ` (kept as <name>)`. The one exception: when the OS refuses the rename even after `media.RENAME_RETRIES` retries, `media.quarantine_note` deletes the file (`… (could not rename <name>: <error>; deleted, so that it does not pass for the episode)`; if not even that works, the note asks for a deletion by hand), because a bad file left under the episode's name would be skipped as done by the next run. `DownloadOptions.verify=False` / `--no-verify` skips the file check only (the Content-Length / aborted-transfer check is unconditional, and so is the DRM check, which runs before it and deletes an encrypted file instead of quarantining it — see the Scope bullet on paid episodes) and is documented as a debugging aid only; do not make verification conditional on anything else.
- One small cover (thumbnail) request per episode in the browser engine: one `GET` of `Episode.cover_url` after its video and only then, outside the media budget (`MAX_COVER_GETS = 1`), never retried, never a second candidate; its failure only appends `; cover: <reason>` to a `done` result (a 429 there is a WARNING, not a stop). The yt-dlp engine delegates the fetch to yt-dlp's `writethumbnail`, which gets the cover just before the video, names it after the cover URL's extension (`.jpeg` for TikTok) and reports nothing when it fails. By default (`DownloadOptions.thumbnail = "embed"`, `--thumbnail`) the cover then goes INTO the MP4 as its cover art — the `covr` atom, written by mutagen in `thumbnails.embed_cover` — and no sidecar stays; `both` keeps the sidecar too, `file` only the sidecar, `none` makes no cover request at all. Never modify a downloaded video in place: embedding edits a copy (`<name>.embed.part`) that replaces the original atomically, and any failure deletes the copy, leaves the video byte for byte and keeps the cover as a file (the message says so; the status never changes). A skipped episode never fetches a missing cover.
- The cloud sandbox and CI cannot reach tiktok.com — never try. Everything network-facing is thin, injectable and tested against `tests/fixtures/` or `tests/integration/fake_tiktok.py`.
- The web UI never serves a path outside `--out`: `GET /api/files/…` streams only the file a job row recorded — a `done` row, and `skipped-exists` rows are served too (a file an earlier run saved) — after resolving it inside `out_dir`, and answers a 404 that names no path to anything else; the save-all ZIP (`GET /api/files/<job>/all`, a finished job only) applies the same check to every entry, before answering and again right before opening each file, so the ZIP never includes a path outside `--out`. Binding `serve` to anything but loopback requires `--token` (or `DRAMAFETCH_TOKEN`; at least 8 cookie-safe characters), which every `/api/*` request must then carry as `Authorization: Bearer <token>` or the `dramafetch_session` cookie; the token value never appears in logs, messages or snapshots (`token: set` / `token: none`).

## The owner's acceptance criteria

What the owner asked DramaFetch to do. Every change keeps all eight true, and every maintenance agent (`download-guardian` and `vuln-sentinel` in the root `.claude/agents/`, `code-reviewer` and `test-runner` in `DramaFetch/.claude/agents/`) judges a change, an upstream release or a defect report against them — inside the Scope above, never against it:

1. **Whole series, in batches.** One link gets every episode the session may play; several links (`download URL [URL ...]`, `--from-file`, the web's "Several series" box, one paste of several lines into the extension's box) run strictly one series after the other — `engine.run_batch` / `run_series`, `extension/src/app/engine.js`. Proven by `tests/test_engine.py`, `tests/test_cli.py`, `tests/test_web.py` and the batch scenarios of `tests/integration/`.
2. **Files named `<Series name> - Episode NN`.** `models.DEFAULT_NAME_FORMAT = "{series} - Episode {number}"`, inside `<Series name> [<series id>]/`; the extension's `lib/naming.js` gives the same names (parity-tested) within Windows' path limits.
3. **Good audio and video, in sync.** The highest-bitrate rendition the account is served (`--quality compatible`: H.264; `best`: any codec), saved as served — nothing is ever re-encoded or remuxed — and every file verified (`media.verify_video` / `lib/mp4.verifyVideo`: parses, nothing cut short, an audio track, the listed duration within max(3 s, 5 %)).
4. **The JPG cover embedded in the MP4.** `--thumbnail embed` (the default) writes the `covr` atom on a copy that replaces the original atomically (`thumbnails.py`, `lib/mp4.embedCover`); the framemd5 proofs in `tests/test_extension_media.py` and integration `test_a` show no decoded frame or sample changes.
5. **Never trigger TikTok's anti-bot systems.** Behave like one person watching: the Pacing floors below, one request at a time, the 30-minute cooldown after a refusal, a full stop on a 429, a captcha, a login wall or 3 failures in a row — and nothing that hides automation (Scope).
6. **Paid episodes the account has unlocked, like Flixcam — nothing more.** `catalog.access_of` decides `free` / `unlocked` / `locked` from what TikTok served the user's own session; locked episodes are listed and skipped; DRM is detected and never decrypted or kept.
7. **A SnapAny-like page.** Paste a link, see the episodes with their covers, download all: `dramafetch serve` (the local web UI) and the Chrome extension's page — no terminal needed for the extension —, where (the owner's decision of 2026-11-20, DramaFetch 1.7.0) a pasted link downloads the whole drama at once and **See episodes** on a library card shows the episodes with their covers to pick from.
8. **Everything works.** The Definition of done below is green on every change; a skipped suite is "not run", never "passed"; what the sandbox cannot reach (TikTok) is verified on the owner's machine (`dramafetch doctor`, `--dump-raw`) before anyone claims it works there.

When an upstream project, a changelog, an issue or a web page shows a way to "fix" a download that would cross the Scope — solving or bypassing TikTok's challenges or captchas (yt-dlp's TikTok extractor does — DramaFetch stops it at one: `downloader.YtDlpChallengeGuard`; a yt-dlp release that changes how it meets them is tried against that guard's test before any floor moves), forging or generating request signatures or tokens, spoofing fingerprints or hiding automation, proxies or IP rotation, faster pacing, unlocking or faking entitlement, DRM keys or `allow_unplayable_formats` — it is never applied, here or in the extension. The agent reports what it saw and what it did not port.

## Pacing

The anti-bot strategy is to behave like one person watching, and it lives in `engine.download_series` with its knobs in `models.DownloadOptions`:

- The defaults are deliberate and are a floor: 4–9 s between episodes (`delay_min_s`/`delay_max_s`), a 60–120 s rest every 10 network attempts (`rest_every`, `rest_min_s`/`rest_max_s`; a failed attempt counts, skips do not), a stop after 3 consecutive failures (`max_consecutive_failures` — three failures in a row across the series of a run: the streak is `PacingState.consecutive_failures`, so it spans the series of a CLI batch and the jobs of the web; a `done`, a stop and an idle gap of `long_rest_min_s` reset it, a series boundary never does), at most 3 yt-dlp retries (`downloader.MAX_RETRIES`) with `sleep_interval_requests: 1`, at most 4 media requests per episode in the browser engine (`downloader_browser.MAX_GETS_PER_EPISODE`) plus at most one cover request (`MAX_COVER_GETS`). Never lower them in code, never make the code itself go below them, never make a pause conditional on "it worked last time". The existing flags accept lower values only so that tests against the fake server run fast; do not add further ways to go below the defaults. Users may raise them (`--pace human`, `--rest-every 5`, …); the only way to make a run lighter is fewer requests (`--engine browser`), never faster ones.
- Never parallelise: one download at a time in the engine, one job at a time in `web/jobs.py`, one browser context in the browser engine. No proxies, no rotation, no second instance.
- Batches (`engine.run_batch` for the CLI, `engine.run_series` per series — the web's batch jobs too) follow three rules that must never be weakened. **Never resolve the series of a batch up front**: each series is resolved right before its own downloads (all lists first would be a burst of page loads, and the signed play URLs would expire before their episodes are reached). **Never drop the series rest or the long break**: between two series that both contact TikTok the batch rests `rng.uniform(rest_min_s, rest_max_s)` (`on_pause("series-rest", s)`, through `run_series(before_network=…)`, before the next resolve and after the cooldown check — the first series, and one that makes no request, need none); across a whole RUN — one `engine.PacingState` for a CLI batch, one for the web job manager's lifetime — every `DownloadOptions.long_rest_every` (100) network attempts bring `"long-rest"`, `long_rest_min_s`–`long_rest_max_s` (15–30 min), in place of that step's pause (before the next resolve when it falls between two series of a CLI batch or two batch jobs of the web — `engine.long_rest_due` — never after it, where the fresh play URLs would wait through it), and an idle gap of `long_rest_min_s` counts as that break (the count restarts); no CLI flag sets any of the three, and none may be added. **Any stop ends the batch**: a `SeriesRun.stop` — a cooldown, a failed resolve (login, captcha, 429, any `DiscoveryError`), a stop status, a failure streak (also on the last episode, reported through `download_series(on_stop=…)`), a cooldown met right before an episode, a `cookies.txt` with malformed lines (`error_kind` `cookies`, `engine.COOKIES_STOP`, before the resolve: every download would refuse it) — makes every remaining series `not started: batch stopped in <name or id> (<reason>)` (`engine.not_started_message`) with no request at all, and `engine.check_cooldown()` is asked before every series and, inside `download_series`, before every network attempt. The complete skip (`models.RECHECK_AFTER_S` = 24 h) fires only for a whole-series run — no episodes spec (not even `all`), no `recheck` / `overwrite` / `include_locked` / `dry_run` — whose manifest (`engine.find_series_dir`: `iterdir` + `endswith(" [<id>]")`, never a glob; `manifest.read_manifest`: no side effects) says complete less than 24 h ago while every file it counted is still on disk (`Manifest.missing_files()` empty); never make it fire on anything weaker. Its report names the episodes the manifest recorded `skipped-locked` as locked (read-only, no rows) and its line then ends with `engine.RECHECK_HINT` (`unlocked more in the TikTok app since? --recheck looks again`). Every input of a CLI batch is parsed before the first request.
- `DownloadStatus.FAILED_BLOCKED` (HTTP 403 / forbidden / access denied from yt-dlp, and its `Your IP address is blocked from accessing this post` — TikTok's status 10204; a JS challenge on a video page, which `downloader.YtDlpChallengeGuard` stops unanswered — `downloader.CHALLENGE_STOPPED_MESSAGE`; a captcha page met by the browser engine's in-session list refresh) and `FAILED_RATE_LIMITED` (HTTP 429) stop the run, like `FAILED_LOGIN`: the remaining episodes get the same status with `stopped: …` and no request is made (`engine._STOP_STATUSES`); `exit_code` returns 5 for both. Do not retry, wait-and-knock or switch engines automatically after one — the user waits 30–60 minutes and resumes with the manifest. The Chrome extension's one automatic retry (1.8.0, the owner's request of 2026-11-21; `extension/src/app/app.js` `queueAutoRetry`) leaves this rule whole: it is queued only for a drama whose run made a request and did NOT stop — any stop (a 403, a 429, a captcha or JS challenge, a login wall, the cooldown, three failures in a row, a refused write, **Stop**, an error) means none, and so does a **Stop** the engine never met (pressed while the job's last episode transferred or during its end: `app.stopRequested`) —, only while no cooldown is in force and no write was refused (`retryAllowed`), only over that run's plain `failed` rows that are not `stopped: …` (never `failed-unavailable`, locked or a stop's rows), once per download (never for an automatic retry's own failures, which wait for the user's **Retry**) and never over episodes a waiting `selection` job of the series holds, or the running one until it is done with its drama (a retry, **Download selected**, **Download all available**; `heldNumbers`, `app.runningDone`); **Stop** takes the automatic retries waiting in the queue out of it at once (`dropAutoRetries`), whatever the running job does; it is exactly the tab's **Retry** queued at the end of the queue — the cooldown gate, the rest between jobs, a fresh list, every pause and the failure streak, which spans jobs — with no timer, no `alarms`, nothing lowered and no request a manual **Retry** would not make. Never add a "wait for the cooldown and try again", a second automatic round or an automatic retry after a stop. The extension's **See episodes** downloads again in full since 3.0.0 (the owner's decision of 2026-11-25; `overwrite`: no done, existing-file or complete skip): every episode it takes then costs its requests like any other — its video and, unless the cover mode is `none`, its cover, after one fresh listing of the series —, with every pause, the rests, the cooldown, the stops and the failure streak unchanged — never faster than a paste. Keep `downloader.classify_error` mapping 403 wordings to `FAILED_BLOCKED` and `\b429\b` to `FAILED_RATE_LIMITED`, and keep the anti-bot rules first: login, then 429, then 403, and only then the DRM wording — a refusal that also names DRM is that refusal (a stop and, for 403 / 429, the cooldown), never a remembered DRM verdict. Both statuses also start the global cooldown (`engine.BLOCK_STATUSES` → `engine.record_block_if_refused` → `cooldown.record_block(message, source=options.engine)`, once per run, before the rest is marked `stopped`; `cli video` does the same for its one result), and so do a `RateLimitedError` or `ChallengeError` raised by the discovery inside `engine.resolve` (source `discovery`) — a captcha before the first list page or after it: `browser._stop_if_challenged` asks the page after an in-page pagination fetch that returned nothing usable and after every scroll round that loaded nothing, so a wall TikTok raises mid-list is a refusal (stop, cooldown), never a partial list to download from; the extension's `discovery.js` does the same. Every path that contacts TikTok asks `engine.check_cooldown()` first — the CLI's `info`/`download`/`video` (`cli._refused_by_cooldown`: `error: <cooldown_message>` on stderr, exit 5, no request; `download --dry-run` still resolves the list, so it is refused too; `video --dry-run` needs no network and is exempt), the web's resolve/download — except the browser engine's in-session list refresh, which runs inside a download that already passed the check. `download_series` asks again right before every network attempt, after its pause: a cooldown another front end recorded meanwhile (during a long break, say) stops the run there — that episode and the rest `FAILED_RATE_LIMITED` with `stopped: cooldown until HH:MM`, `on_stop("cooldown until HH:MM")`, not recorded a second time. `COOLDOWN_MINUTES` is 30; do not lower it, do not add a flag that skips the cooldown (deleting the file is the documented, deliberate way to lift it).
- Every pause goes through `on_pause(kind, seconds)` then the injectable `sleep`; skips (manifest, a DRM verdict the manifest remembers, locked, existing file, dry run) never pause and never count. Tests use a fake `sleep` and a fixed `rng` — a test that really sleeps is a bug. A test never touches `~/.dramafetch`: `tests/conftest.py` sets `DRAMAFETCH_STATE_DIR` to `tmp_path` for every test (the autouse fixture `dramafetch_state_dir`, unit and integration alike; CLI subprocesses inherit it), so `cooldown.json` lands in the test's own directory.

## Architecture (`src/dramafetch/`)

| Module | Role |
| --- | --- |
| `models.py` | Dataclasses (`SeriesRef`, `VideoRef`, `Episode`, `Series`, options, `DownloadStatus`, `DownloadResult`) and the `Discovery` / `Downloader` protocols — pure data, shared by everything; `THUMBNAIL_MODES` (`embed` `both` `file` `none`) and `DownloadOptions.thumbnail` with its `thumbnails` / `embed_cover` / `keep_cover_file` properties; `QUALITY_MODES` (`compatible` `best`) and `DownloadOptions.quality` (default `compatible`), `DownloadOptions.verify` (default True), `Episode.quality_hint` (`"720p h264"`: the label of the rendition the default quality takes, None without one); `RECHECK_AFTER_S` (24 h: a series complete less recently than that is resolved again), `DownloadOptions.long_rest_every` / `long_rest_min_s` / `long_rest_max_s` (100 network attempts of a run, 900–1800 s: no CLI flag) and `DownloadOptions.recheck` (`--recheck`); `ACCESS_MODES` (`free` `unlocked` `locked`) and `Episode.access` / `paid` / `drm` (after `quality_hint`, before `raw`) — `access=""` derives `locked` from a non-empty `lock_hints` (or `drm`), else `free`, so a caller that sets only `lock_hints` keeps its build-6 meaning, and an access equal to that derivation follows later assignments of `lock_hints` / `drm` (also on a `dataclasses.replace` copy); a value outside `ACCESS_MODES`, or `drm` without `locked`, is a ValueError; `locked` is `access == "locked"`; `DRM_MARK` (`protected by DRM`: every DRM message starts with it), `DRM_MESSAGE` (`protected by DRM (encrypted tracks): DramaFetch does not decrypt it`: the verdict of a downloaded file, both engines, and of yt-dlp's own "DRM protected") and `DRM_REMEMBERED_MESSAGE` (`protected by DRM (found by an earlier run): DramaFetch does not decrypt it; --include-locked tries again`: the skip of a remembered verdict, written by `engine`); `RECHECK_HINT_TAIL` (`--recheck looks again`: the tail `engine.RECHECK_HINT` is built from and the short-served message carries — the extension's `display` maps it to its checkbox), `SHORT_SERVED_PREFIX` (`TikTok serves this episode short: `: every short-served message starts with it) and `SHORT_MARK` (`short`: the quarantine word of such a file) |
| `errors.py` | Exception hierarchy; each class maps to one CLI exit code — except `ThumbnailError`, which never escapes an engine (a cover that cannot be embedded is kept as a file and reported in the message), and `MediaError` (a saved file is not an MP4 mutagen can read), which `media.verify_video` turns into a reason |
| `media.py` | Integrity of a saved video, shared by both engines: `probe_video(path)` → `VideoProbe(duration_s, has_audio, audio_codec)` through mutagen (a video-only MP4 gives `has_audio=False`, never raises; a non-MP4 raises `MediaError`), `atom_problem(path)` (the top-level atom walk: a `KNOWN_ATOMS` member whose declared size runs past the end of the file → `truncated MP4 (<atom> atom cut short: <have> of <need> bytes)`; ## Extension (`extension/`)

DramaFetch for Chrome is a second front end — a Manifest V3 extension for users without Python (Windows first) — that re-implements the engine in plain ES2022 modules: `// @ts-check` and JSDoc types in every file, no npm dependency at all (Node built-ins only in its tests), no CDN or remote resource. The Python package is not touched by it. The Scope and Pacing sections above bind it exactly as they bind the Python tool; the parity test (`tests/test_extension_parity.py`, `tests/test_extension_media.py`) proves its texts, constants and decisions equal the Python ones.

- **The line.** Only what TikTok serves to the user's OWN logged-in Chrome session. Never unlock, buy, fake or claim entitlement, send a payload field back, reuse a preview's or another account's URL, re-sign or guess a URL, or decrypt/strip DRM; encrypted media is never saved. No stealth, no tampering: never patch, wrap or override anything in TikTok's page (no fetch/XHR monkeypatching, no navigator/UA spoofing), never `chrome.debugger`, never read cookies (the page's own requests carry the session), never change a request of TikTok's page. Its only header changes are on its OWN media, cover and thumbnail requests — `Referer: https://www.tiktok.com/` set and `Origin` removed, what the Python browser engine's Playwright request and yt-dlp send — through one declarativeNetRequest SESSION rule whose `initiatorDomains` is the extension itself (`downloader.refererRule` / `applyRefererRule`: `requestDomains` = `TIKTOK_DOMAINS` in production, a `urlFilter` on the test origin in test mode). Those requests go out with `redirect: "manual"`; a redirect is followed only through `redirects.fetchFollowing` (see the permissions bullet). The discovery observes the series tab's requests with `chrome.webRequest` (URLs and status codes only, never bodies, never blocking), the app page observes `onBeforeRedirect` for its own requests (`src/app/redirects.js`: the target URL only, registered for the DramaFetch tab only, filtered to the host permissions, to the extension's own initiator and to the current request of each URL), and the discovery fetches the list pages with `chrome.scripting.executeScript({world: "MAIN"})` running the page's own `fetch` (`discovery.fetchInPage`, the port of `browser.FETCH_JS`); scrolling and the captcha check run in the ISOLATED world. One request at a time, one job at a time (a Web Lock makes one app tab per browser the engine), never every list of a batch up front. The user's TikTok favorites (the owner's decision of 2026-11-15: the entries of the profile's **Favorites** → **Drama** list are buttons, so no link item can show on them): the background worker OBSERVES, at its top level, the `drama_list` requests of the user's own TikTok tabs (`chrome.webRequest.onCompleted` filtered to the URLs holding `drama_list` on TikTok's hosts — in test mode also on the test copy's plain-http host —, so Chrome hands the worker no other request of those tabs and starts it for none; CI runs the same sequence in the `dramafetch` job of `../.github/workflows/ci.yml` (Node 22 for the extension's `node --test` and type check, Python 3.12, a full ffmpeg — `sudo apt-get -o Acquire::Retries=3 install -y --no-install-recommends ffmpeg` — before the unit tests, then Playwright's browsers restored from `actions/cache` (`~/.cache/ms-playwright`, keyed on the runner OS and the Playwright version installed in the job), `playwright install --with-deps chromium` (on a cache hit it only checks Chromium's OS dependencies) and `pytest -m integration` with `DRAMAFETCH_CHROMIUM` pointing at the installed browser). The job has `timeout-minutes: 60` (about three times a run on a slow apt mirror), so a hang ends red instead of running on. It sets `DRAMAFETCH_REQUIRE_TOOLS: "1"`, so a test that would skip for a missing node, ffmpeg or Chromium fails there instead (`tests/conftest.py`: `REQUIRE_TOOLS_ENV`, the `tools` fixture, a `pytest_runtest_setup` hook for the integration modules' `no Chromium at …` skips); environment skips such as "no IPv6 loopback" stay skips. It uploads the extension's runtime files — `manifest.json`, `_locales`, `icons`, `src` — as the artifact `dramafetch-extension`, which users can unzip and load unpacked.

## Definition of done

1. `ruff check`, `ruff format --check`, `mypy` and `pytest` are green; `pytest -m integration` too when a Chromium is available; and, from `extension/`, `node --test` and the `tsc` check. Report the real output.
2. Anything users see — flags, exit codes, output layout, statuses, API routes, pacing defaults — is reflected in `README.md` (flags table, exit codes, "Pacing and TikTok's protections"); a new or moved module appears in the table above.
3. No cookie value anywhere, no bypass of any kind, no parallel downloads, no new dependencies.
4. Fixtures and `tests/integration/fake_tiktok.py` were updated whenever TikTok's payload shape changed.
5. A change users can see bumped the version in the four places named under Conventions and added its `CHANGELOG.md` entry.

## Agents

Four agents maintain DramaFetch. Each judges a change, an upstream release or a defect report against the Scope and the owner's acceptance criteria above, and none commits, pushes or merges — the shift (or `repo-steward`) commits and pushes under the repository's branch and PR rules, and a human merges (or `merge-steward`, for a PR that passes the merge gate).

| Agent | Where | Does |
| --- | --- | --- |
| `download-guardian` | `../.claude/agents/` | Keeps the downloads meeting the criteria: runs `../.claude/scripts/dramafetch-watch.sh` and the definition of done (`DRAMAFETCH_REQUIRE_TOOLS=1`; in the nightly shift it takes the shift's results instead of running it again), reads what changed upstream — yt-dlp's TikTok extractor and changelog, Playwright, mutagen, curl_cffi, Chrome's extension platform — from primary sources only, and ships the smallest cited fix in both front ends; majors, new permissions and indirect evidence become issues. The DramaFetch steps of the nightly maintenance shift |
| `vuln-sentinel` | `../.claude/agents/` | Read-only vulnerability watch: every installed distribution against PyPI's per-version OSV data, yt-dlp's security notes, the extension's permissions, CSP and message handling, the web UI's token, Host guard and `--out` confinement, committed cookie values, the `dramafetch` CI job. The DramaFetch part of the weekly security review |
| `code-reviewer` | `.claude/agents/` | Read-only review of every DramaFetch diff against the Scope, the criteria, the pacing floors, privacy, Python–extension parity and cited TikTok facts, before every DramaFetch PR |
| `test-runner` | `.claude/agents/` | Runs the definition of done (`haiku`) and reports the counts and only the failures; a skipped suite is "not run" |

A DramaFetch pull request reaches `main` only through the merge gate (`../.claude/shifts/merge-gate.md`) or a human: the gate runs this whole definition of done itself with `DRAMAFETCH_REQUIRE_TOOLS=1` (integration included) on the PR merged into `main`, refuses a PR whose suites lost tests, and needs an independent review of code changes and `download-guardian`'s verdict on a yt-dlp, Playwright, curl_cffi or mutagen bump. It never merges a change to the Scope, the acceptance criteria, the legal notice, the extension's permissions or a download rule (pacing, cooldown, retries, `YtDlpChallengeGuard`): those wait for the owner.

The upstream watch is `tools/upstream_watch.py` (standard library only; covered by `ruff` and `mypy` and by `tests/test_upstream_watch.py`), run through `../.claude/scripts/dramafetch-watch.sh`: PyPI's JSON API (the latest releases, and each installed version's vulnerabilities from OSV), yt-dlp's raw `Changelog.md` and `yt_dlp/extractor/tiktok.py` at the installed release's git tag (`yt_dlp.version.__version__` of the inspected interpreter — PyPI's `2026.8.19` is the tag `2026.08.19`; `tag_of` pads the version the same way when that cannot be read) and at `master` (with the names DramaFetch reads in TikTok's payload — the literals of `catalog.py`, `discovery/browser.py` and `urls.py` — that the extractor stopped or started quoting), and Chrome Stable from Google's version history API next to the extension's `minimum_chrome_version`. Whatever it could not check — a source that did not answer, a direct dependency not installed or not checked, the extractor not compared, Chrome Stable not read — is an Attention item too, so `nothing new` means everything was compared. It never contacts TikTok; its report is evidence for an agent, never a decision, and nothing found upstream moves the line drawn in the Scope. From the repository root, where a session lists only the root agents, the shifts run `code-reviewer` and `test-runner` as a `general-purpose` subagent that follows the agent's file.

3. Update the facts in `urls.py`, `README.md` and this file in the same PR, with the date they were verified.
