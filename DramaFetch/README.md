# DramaFetch

[![CI](https://github.com/brunocarbone98/projects/actions/workflows/ci.yml/badge.svg)](https://github.com/brunocarbone98/projects/actions/workflows/ci.yml)

DramaFetch downloads the episodes of a TikTok short drama that your own TikTok account can already watch — a whole series at a time instead of one video after another — for personal offline viewing. You paste the series URL; it discovers the episode list the way TikTok's own web app does, hands each episode to [yt-dlp](https://github.com/yt-dlp/yt-dlp) — or, with `--engine browser`, fetches it inside one browser session of its own — paces itself like one person watching, remembers what it already has so interrupted runs resume, and lists (then skips) the episodes that are locked. There is a CLI and a small local web UI; both drive the same engine.

> **Legal notice.** DramaFetch is for personal, offline viewing of episodes that your own TikTok account can already watch. It does not unlock paid episodes and does not bypass DRM or access controls; locked episodes are listed and skipped. Downloading may breach TikTok's Terms of Service, and the videos belong to their creators and studios — you are responsible for how you use this tool.

> **Built without access to TikTok.** This tool was written in a sandbox that cannot reach tiktok.com. Every network-facing piece is thin and injectable, tested against hand-written payload fixtures that follow the documented `item_list` shape and a local fake TikTok server — never against TikTok itself. The first real run is the real test: start with `dramafetch doctor`, then `dramafetch info URL --cookies cookies.txt --dump-raw raw/`, and read [Troubleshooting](#troubleshooting) if the episode list looks wrong.

## How it works

Verified facts (October 2026) that the code depends on. They are also recorded in the docstring of `src/dramafetch/urls.py`; when TikTok changes, update both (see [`CLAUDE.md`](./CLAUDE.md)).

- A series URL looks like `https://www.tiktok.com/shortdrama/episode/7675706520839033876/8`. The long number is the **series id** (TikTok calls it `dramaID` in its API), _not_ a video id; the trailing number is only the 1-based episode you were watching.
- yt-dlp does not recognise `/shortdrama/` URLs ([yt-dlp/yt-dlp#17725](https://github.com/yt-dlp/yt-dlp/issues/17725), open) — that gap is why this tool exists. yt-dlp _does_ download each episode's ordinary video page, `https://www.tiktok.com/@<user>/video/<item_id>`; the `@user` segment is not checked, so `@_` works.
- TikTok's web app lists episodes through `GET /api/drama/episode/item_list/?dramaID=<series_id>&cursor=<c>&count=<n>&…` (plus its usual web parameters and signatures). Each item carries the episode's video id, `dramaInfo.dramaID` and `dramaInfo.DramaVideoData.EpisodeNumber`; episode order comes from `EpisodeNumber`, never from upload time, and items whose `dramaID` differs from the series are dropped. `GET /api/drama/detail/` adds the series name and the announced total, which is how gaps are detected.
- DramaFetch therefore opens the series page in a real Chromium (Playwright), captures those API responses as the page makes them, paginates the way the page does — same request, next `cursor` — and builds the episode list. A static strategy reads the JSON TikTok embeds in the page (`__UNIVERSAL_DATA_FOR_REHYDRATION__`) when that is enough; `--strategy auto` tries static first and falls back to the browser.
- Without a logged-in TikTok session the list endpoints return nothing and the videos have no play address; yt-dlp then reports "No video formats found" or lands on `/login`. A `cookies.txt` exported from your logged-in browser is the normal way to run (see [Cookies](#cookies-you-will-need-them)). Cookie values are never printed, logged, dumped or sent anywhere but TikTok.
- Paid episodes: TikTok sells later episodes for coins. Items that look locked (`isFree=false`, `isLocked`, a price, an empty play address) are listed with those hints and skipped by default. Nothing in DramaFetch unlocks, bypasses or fakes entitlement.
- Politeness: one download at a time, a random 4–9 s pause between episodes, a 60–120 s rest every 10 downloads, 0.8–1.6 s between list pages, a full stop on HTTP 403, HTTP 429 or three failures in a row — and, after a 403, a 429 or a captcha, a 30-minute cooldown during which nothing contacts TikTok at all — see [Pacing and TikTok's protections](#pacing-and-tiktoks-protections).
- Integrity: every saved video is checked (a parseable MP4, not cut short, with audio, about as long as the list says) before its cover is handled; a file that fails is kept as `<name> (incomplete).mp4`, the episode is `failed` and a rerun tries it again — see [Integrity](#file-names-and-thumbnails).

## Pacing and TikTok's protections

TikTok protects its site against bulk downloading, and a whole series is 30+ requests in a row — exactly what that protection looks for. DramaFetch does not try to defeat it (no proxies, no stealth, no parallelism); it behaves like one person watching a series, which is the only approach that keeps working:

- **One request at a time.** Episodes are downloaded strictly one after another, in ascending order — in the CLI and in the web UI, where jobs queue. Never run two instances at once.
- **A pause between episodes.** A random 4–9 s by default (`--delay-min` / `--delay-max`). `--pace human` waits instead about as long as the episode you just downloaded lasts — its duration, at least `--delay-min`, plus 0–3 s of jitter, at most 300 s — the rhythm of someone actually watching.
- **A longer rest every few episodes.** After every 10 episodes that needed the network — a failed attempt counts too — (`--rest-every`, 0 disables) a 60–120 s rest (`--rest-min` / `--rest-max`).
- **Randomised pauses between list pages.** While the episode list is discovered, the pause before each further `item_list` page is 0.8–1.6 s: the 0.8 s minimum times a random factor between 1 and 2, drawn afresh every time (the hidden `--page-delay` sets the minimum), so paging never ticks like a metronome.
- **Stop at the first sign of trouble.** An HTTP 403 (status `failed-blocked`), an HTTP 429 (`failed-rate-limited`) or a login redirect (`failed-login-required`) stops the run at once, and so do 3 failures in a row (`--max-consecutive-failures`, 0 disables). The remaining episodes are marked `stopped: …` without one more request; nothing retries on its own. Wait 30–60 minutes, then run the same command again: the manifest resumes where the run stopped.
- **Never knock again right after a refusal.** A refusal — HTTP 403 or 429 from a download, HTTP 429 or a captcha page while the list is being resolved — also starts a **30-minute cooldown**: until it ends, `info`, `download` and `video` exit 5 before making a single request (`error: TikTok refused a request at 14:02 (…); DramaFetch waits until 14:32 (27 min left) before contacting TikTok again — delete … to lift it, at your own risk`), the web UI answers 429 and `dramafetch doctor` shows a `cooldown` line. The cooldown is one small file, `~/.dramafetch/cooldown.json` (`DRAMAFETCH_STATE_DIR` relocates the folder), shared by every DramaFetch command on the machine. There is deliberately no flag to skip it: knocking again right after a refusal is exactly what makes TikTok's protection escalate from one refused request to a blocked session or address, and a flag would be used in that very moment. Deleting the file lifts it — at your own risk.
- **Fewer requests overall.** Skips (manifest, locked, existing file) cost nothing; yt-dlp is held to at most 3 retries with a one-second gap between its own requests; and `--engine browser` (next paragraph) downloads a series with about half the requests.
- **One list per quarter of an hour in the web UI.** `serve` keeps every resolved episode list in memory for 15 minutes: **Resolve** followed by **Download all free** costs one discovery, not two, and resolving the same series again within that time costs nothing (**Refresh list** fetches it again) — see [Web UI](#web-ui).

**Fewer requests: `--engine browser`.** The episode list TikTok's web app loads already names each episode's signed play URLs (`video.bitrateInfo[*].PlayAddr.UrlList` and `video.playAddr`, valid for a few hours — the `expire` parameter). The default engine ignores them and hands every episode to yt-dlp, which loads the episode's video page and then the video, from a second client. `--engine browser` instead fetches those play URLs directly, inside one Chromium session of its own, set up like the discovery's — your `cookies.txt`, the same Chrome user agent, one `GET` per episode (plus one small one for the cover, unless `--thumbnail none`): no per-episode page load, about half the requests. When the URLs have expired (a long run, a list resolved a while ago) it opens the series page once more in that same session, takes the fresh list and keeps it for the rest of the run, so a 30-episode run refreshes once, not 30 times. A 403, 404 or 410 on a URL moves on to the episode's next listed URL, then to a fresh list, and only then is the episode `failed-unavailable` — within a budget of 4 requests per episode, so a locked or region-restricted episode never becomes a burst of requests against every mirror; any other HTTP error fails the episode at once (no next URL, no fresh list), and so does a transfer cut short — fewer bytes than the announced `Content-Length`, or a connection the server dropped — (`failed`, `download looks incomplete or wrong: truncated body …`: the network failed, not the URL, so no other mirror is knocked). A 429 is `failed-rate-limited` and stops the run as usual, and so does a captcha page met while refreshing the list (`failed-blocked`, exit 5: rerun with `--headful` and solve it). Use it when yt-dlp trips the protection (HTTP 403, `failed-blocked`): `dramafetch download URL --cookies cookies.txt --engine browser`. `--browser-channel`, `--browser-path` and `--headful` apply to this engine too; each episode is fetched into memory (short-drama episodes are a few tens of MB), written as `.part` and renamed when complete; the engine needs the episode list, so it is for `download` and `serve`, not for `video`. It downloads only what the list offers to your account — nothing is unlocked, re-signed or guessed.

Pauses are printed on stderr as they happen (`… pausing 7 s`, `… resting 95 s after 10 downloads`), and so is the reason a run stopped, so a quiet terminal is not a stuck one; `dramafetch doctor` prints the defaults in one line and whether a cooldown is in force (`– cooldown: none` / `✗ cooldown: until 14:32 (27 min left): <reason>`). The thresholds are TikTok's and unknown, and they change: the defaults are a floor, not a recommendation. For a long series raise them — `--delay-min 8 --delay-max 20 --rest-every 5`, or `--pace human` — and let the run take an hour; that is still faster than a 403 followed by a 30–60 minute wait.

## Install

Python 3.11 or newer.

```bash
cd DramaFetch
python -m venv .venv && . .venv/bin/activate
pip install -e ".[impersonate,dev]"   # impersonate: curl_cffi so yt-dlp presents a real browser's TLS fingerprint; dev: pytest, ruff, mypy
playwright install chromium           # the browser that discovers the episode list …
dramafetch doctor                     # … or skip it and use the Chrome/Edge you have: --browser-channel chrome|msedge
```

`ffmpeg` is optional: TikTok episodes are single progressive files, nothing needs merging.

## Cookies (you will need them)

1. Log in to tiktok.com in your browser and open an episode of the series to make sure you can watch it.
2. Export the site's cookies in Netscape `cookies.txt` format with a browser extension such as "Get cookies.txt LOCALLY" (Chrome/Edge) or "cookies.txt" (Firefox). Export only tiktok.com.
3. Save the file where you run DramaFetch (`cookies.txt` is gitignored here) and pass `--cookies cookies.txt` to every command.

The file is a key to your TikTok account: keep it private, never share or commit it, and expect it to expire after some weeks — when discovery starts failing with login errors, export a fresh one. `dramafetch doctor --cookies cookies.txt` reports its age, how many `.tiktok.com` lines it has and whether a session cookie (`sessionid` / `sid_tt`) is present — names only, never values. It also flags malformed lines (not seven tab-separated fields, or a non-numeric expiry) by line number: yt-dlp would skip such a line with a warning that quotes it whole, cookie value included, so `download` and `video` refuse a file with malformed lines until it is fixed or re-exported. For the download step yt-dlp can alternatively read cookies straight from a browser profile with `--cookies-from-browser chrome`; the discovery step still needs the file.

## Usage

```bash
dramafetch doctor --cookies cookies.txt                   # environment check: Python, yt-dlp, curl_cffi, Playwright, browser, ffmpeg, cookies, mutagen, cooldown
dramafetch info URL --cookies cookies.txt                 # list the episodes: #, item id, duration, quality (e.g. 720p h264), title, free|locked + hints, warnings, target folder
dramafetch info URL --cookies cookies.txt --json          # the same as JSON (feed it to scripts)
dramafetch download URL --cookies cookies.txt             # every free episode into ./downloads/<Series name> [<series id>]/
dramafetch download URL --cookies cookies.txt --episodes 1-10,12,20-   # a selection: ranges, single numbers, open-ended "20-"
dramafetch download URL --cookies cookies.txt --dry-run   # show what would be downloaded, touch nothing
dramafetch download URL --cookies cookies.txt --pace human --engine browser   # a long series: pace like a viewer, about half the requests
dramafetch download URL --cookies cookies.txt --name-format "{series} - Episode {n} - {title}"   # your own file names (placeholders below)
dramafetch download URL --cookies cookies.txt --thumbnail both   # also keep each cover as a .jpeg next to its video (Plex, Jellyfin, Kodi)
dramafetch download URL --cookies cookies.txt --thumbnail none   # the videos only, no cover at all
dramafetch download URL --cookies cookies.txt --quality best   # the highest bitrate whatever the codec (H.265 needs a capable player); default: the best H.264
dramafetch video https://www.tiktok.com/@user/video/<id> --cookies cookies.txt   # one ordinary video, no discovery: <id>.mp4, its cover embedded
dramafetch serve --cookies cookies.txt                    # the web UI on http://127.0.0.1:8765/
```

`URL` is the series URL (any episode of it) or just the bare series id. Short links (`vm.tiktok.com/…`) are not expanded: open them in the browser and paste the full address.

### File names and thumbnails

Every episode is saved as `<Series name> - Episode <NN>.mp4` — `The Billionaire's Secret Heiress - Episode 01.mp4` — with its cover embedded in the file as its cover art (with `--thumbnail both` also, and with `file` only, as `<same name>.jpeg` next to it — `.jpg` / `.png` / `.webp` with `--engine browser`) — see **Thumbnails** below. `--name-format FORMAT` changes the name. The placeholders are replaced one by one and nothing else in braces is accepted (`{number:02d}` is an error: the padding is built in); the result is made safe for every OS — `/`, `\`, `:`, `|`, `?`, `*` and the like become spaces, so a format cannot create sub-folders, and a trailing dot or a Windows device name such as `CON` is defused — and cut to 150 characters:

| Placeholder | Expands to | Example |
| --- | --- | --- |
| `{series}` | The series name (at most 80 characters); `series-<id>` when TikTok gives none, `video` for `dramafetch video` | `The Billionaire's Secret Heiress` |
| `{number}` | The episode number, zero-padded to two digits | `01`, `12`, `100` |
| `{n}` | The episode number as is | `1`, `12`, `100` |
| `{title}` | The episode title — TikTok's description — at most 60 characters | `The Billionaire's Secret Heiress Episode 1` |
| `{id}` | The TikTok item (video) id | `7699400000000000001` |

A format must contain at least one of `{number}`, `{n}`, `{title}` or `{id}`: `{series}` alone would give every episode the same name, and every episode after the first would be skipped as already existing. `dramafetch video` has no series, so its default is `{title}`, which for a bare video URL is the item id — `7699400000000000001.mp4`. The manifest records the file each episode landed in, so a run resumes whatever format it uses; files from an earlier run under a _different_ format are found through the manifest only, not by name.

**Thumbnails.** By default the episode cover goes _into_ the MP4 (`--thumbnail embed`): it is written as the file's cover art — the `covr` metadata atom, the place iTunes, the Apple TV app, Infuse, VLC's media library and most music-style players read — so the video carries its poster wherever you copy it and no image file clutters the folder. Windows Explorer, Finder and phone galleries ignore that atom and show a frame of the video instead, and Plex, Jellyfin and Kodi prefer a poster file next to the video: that is what the other modes are for — `--thumbnail both` embeds the cover _and_ keeps it as `<same name>.jpeg` (`.jpg` / `.png` / `.webp` with `--engine browser`), `--thumbnail file` keeps only the file (nothing embedded), `--thumbnail none` asks for no cover at all. The embedding is done by [mutagen](https://mutagen.readthedocs.io/) — pure Python, a runtime dependency, the library yt-dlp itself uses for the job; no ffmpeg, no AtomicParsley — and it never touches a downloaded video in place: the cover is written into a copy named `<name>.mp4.embed.part` in the same folder, which then replaces the original atomically; if anything fails the copy is deleted and the video stays byte for byte as downloaded. Only JPEG and PNG can live in a `covr` atom; TikTok's covers are JPEG (`originCover`, `cover`) and only its `dynamicCover` is WEBP.

Each engine fetches the cover its own way. The default `yt-dlp` engine leaves that to yt-dlp's `writethumbnail` (no postprocessor, no ffmpeg): yt-dlp fetches the cover just before the video, names the file after the cover URL's own extension — `<same name>.jpeg` for TikTok's covers (a `dynamicCover` fallback lands as `.image` and is renamed after its bytes) — tries the next cover its extractor listed when one fails, and says nothing when none can be had; DramaFetch then embeds that file into the MP4 and, unless `both`, deletes it. With `--engine browser` the cover is one `GET` of the cover URL the episode list names (`video.originCover`, else `video.cover`, else `video.dynamicCover`), made only after the video is on disk and outside that engine's budget of 4 media requests per episode, never retried and never a second candidate; the body is embedded and/or written as `.jpg`, `.png` or `.webp` after the image type. Whatever happens to the cover, the episode stays `done`; its message — recorded in `dramafetch.json` and shown in the web UI row (the terminal line of a `done` episode prints the file path followed by this cover note, e.g. `E01  done  …/The Billionaire's Secret Heiress - Episode 01.mp4 + cover embedded`; `--dry-run` prints the message) — ends with one of these suffixes:

| Message suffix | Meaning |
| --- | --- |
| ` + cover embedded` | `embed`: the cover is in the MP4, no file next to it |
| ` + cover embedded + file` | `both`: in the MP4 and next to it |
| ` + cover file` | `file`: next to the video only, nothing embedded |
| `; cover: webp cannot be embedded; file kept` (yt-dlp) / `; saved as file` (browser) | A WEBP cover cannot live in a `covr` atom: it is kept as `<same name>.webp` instead, whatever the mode |
| `; cover: could not embed (<reason>); file kept` / `; saved as file` | mutagen is not installed (the reason says `pip install mutagen`), the file is not an MP4 mutagen can write to, or mutagen failed: the video is untouched and the cover is kept as a file, so nothing is lost |
| `; cover: too large, not kept` | Over 5 MiB: an error page or abuse, not a cover — neither saved nor embedded |
| `; cover: not available` | yt-dlp got no cover (it fetches it silently and reports nothing) |
| `; cover: not a JPEG, PNG or WEBP image; file kept` / `; cover: <OS error>; file kept` | yt-dlp wrote a `<same name>.jpeg` that is not an image (an error page) or the file could not be read: it is left as it is, nothing embedded |
| `; cover: HTTP 429 from <host>`, `; cover: HTTP 404 from <host>`, `; cover: <reason>` | `--engine browser`: the one cover request failed (a 429 there is logged as a warning; if TikTok is really limiting, the next video request stops the run as usual) |

With either engine an episode skipped because its video already exists does not go and fetch a missing cover (delete the video, or pass `--overwrite`, to get both), and `--dry-run` prints ` + cover` where a cover would be fetched. Without mutagen — `dramafetch doctor` then says `✗ mutagen: not importable — covers are saved as files only (pip install mutagen)` — `embed` and `both` fall back to the file and the message says so. The web UI's `thumbnail` flag means "a cover is available", embedded or as a file, and its **Cover** link serves whichever exists. A lone `<name>.jpeg` / `.jpg` never counts as "the episode exists": only `.mp4`, `.m4v`, `.mov`, `.mkv` and `.webm` do, and only under exactly the episode's name (`Ep 1.5.mp4` is never `Ep 1`'s file).

**Quality.** Audio and video come in one file: TikTok episodes are single muxed MP4s, so nothing is merged, nothing is re-encoded and ffmpeg is not involved — DramaFetch only _chooses_ among the renditions TikTok lists for the episode (`video.bitrateInfo`: a codec, a bitrate and a `GearName` such as `normal_720_0` or `adapt_lower_1080_1` each), and the source's top rendition is the ceiling. `--quality compatible` (the default) takes the highest-bitrate **H.264** rendition, which every player, TV and phone handles (yt-dlp: `best[vcodec^=h264]/best[vcodec=avc1]/best`; `--engine browser`: the H.264 play URLs by bitrate descending, then the other codecs, then `video.playAddr`). `--quality best` takes the **highest bitrate whatever the codec** (yt-dlp: `best`; the browser engine: every rendition by bitrate descending) — on TikTok that is often `bytevc1`, its H.265 variant, which is smaller and sharper but needs a player with H.265 support (VLC, mpv, recent TVs and phones; an older Windows box or a web browser may show a black picture). `info` prints a `quality` column with the rendition the default mode would take — `720p h264`, `1080p bytevc1`, `-` when the list names none — and `info --json` carries it as `quality_hint`.

**Integrity.** Every saved video is verified before anything else happens to it, so a half-downloaded or wrong file never passes for an episode (`--no-verify` turns this off; it is a debugging aid, nothing more). The check — done with [mutagen](https://mutagen.readthedocs.io/), the library that also embeds the covers; no decoding, no ffmpeg — asks four things of the file: it parses as an MP4; none of its atoms is cut short (a transfer that stopped early leaves an `mdat` shorter than its header says; mutagen alone would not notice, so the top-level atoms are walked); it has an audio track; and it lasts about as long as the episode list said (TikTok's `duration`, a whole number of seconds: a difference beyond 3 s or 5 % fails it — a locked episode served as a 20-second preview is exactly what this catches; `dramafetch video` has no list, so its duration is not judged). `--engine browser` additionally fails a transfer whose body is shorter than the announced `Content-Length`, or that the server cut off, without trying another mirror (that is the network, not the URL). A file that fails is **not deleted but renamed** `<same name> (incomplete).mp4` (`(incomplete 2)`, … when that exists — nothing is ever overwritten), the yt-dlp engine deletes the cover it had saved, no cover is fetched or embedded for it, and the episode is `failed` with `download looks incomplete or wrong: <reason> (kept as <name>)` — `not a valid MP4 (…)`, `truncated MP4 (mdat atom cut short: 1200000 of 13087000 bytes)`, `no audio track`, `duration 20 s, expected 120 s`. The quarantined file never counts as the episode (its name differs), the manifest records `failed` with the message, so the next run downloads the episode again; look at the `(incomplete)` file if you want to know what TikTok sent, delete it when you are done.

### Output layout and resuming

```text
downloads/
└── The Billionaire's Secret Heiress [7699393770256782354]/
    ├── The Billionaire's Secret Heiress - Episode 01.mp4   ← the video, its cover embedded as the MP4's cover art
    ├── The Billionaire's Secret Heiress - Episode 02.mp4
    └── dramafetch.json        ← the manifest: status, path and message per episode
```

With `--thumbnail both` (or `file`) each episode also gets its cover as a file next to it:

```text
    ├── The Billionaire's Secret Heiress - Episode 01.mp4
    ├── The Billionaire's Secret Heiress - Episode 01.jpeg  ← the cover file (.jpg / .png / .webp with --engine browser)
    ├── The Billionaire's Secret Heiress - Episode 02.mp4
    ├── The Billionaire's Secret Heiress - Episode 02.jpeg
```

A video that failed the [integrity check](#file-names-and-thumbnails) stays next to the others under a name the tool never mistakes for the episode:

```text
    ├── The Billionaire's Secret Heiress - Episode 03 (incomplete).mp4   ← kept for inspection; the episode is `failed` and the next run downloads it again
```

File names follow `--name-format` ([above](#file-names-and-thumbnails); two digits, three from episode 100 up) and are sanitised for every OS. `dramafetch.json` is written after every episode, so an interrupted run — Ctrl+C, a 429, a dropped connection — resumes where it stopped, whatever name format it uses: run the same command again and the finished episodes are reported as `skipped-exists` without touching TikTok. `--overwrite` ignores the manifest.

Per-episode statuses: `done` · `skipped-exists` · `skipped-locked` · `dry-run` · `failed-login-required` · `failed-unavailable` (locked, region-restricted, removed or private) · `failed-rate-limited` (HTTP 429) · `failed-blocked` (HTTP 403: TikTok refused the request) · `failed` (including `download looks incomplete or wrong: …`, a video that failed the integrity check and was kept as `(incomplete)`). A login, 403 or 429 failure stops the run, and so do 3 failures in a row; the remaining episodes are marked `stopped: …` without contacting TikTok, and a 403 or 429 starts the 30-minute cooldown (see [Pacing](#pacing-and-tiktoks-protections)).

### Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Everything selected is done, skipped (exists / locked) or dry-run |
| 1 | Another DramaFetch error (the message says what) |
| 2 | Usage error (inconsistent pacing flags, an invalid `--name-format`, …), unsupported URL, or at least one episode failed — also a run stopped after 3 failures in a row |
| 3 | TikTok wants a login: export fresh cookies and pass `--cookies` |
| 4 | Discovery failed: a captcha / "verify you are human" page (try `--headful`), an HTTP error such as 403 for the series page, or no episode list arrived |
| 5 | Rate limited (HTTP 429) while listing the episodes, or — while downloading them — blocked (HTTP 403, `failed-blocked`; with `--engine browser` also a captcha page met while refreshing the list) or rate limited (HTTP 429, `failed-rate-limited`): wait 30–60 minutes, then run the same command to resume (no other strategy is tried, nothing retries on its own; after a captcha, rerun with `--headful` and solve it). Also, with the same code, `info`, `download` or `video` refusing to contact TikTok at all because such a refusal happened less than 30 minutes ago — the **cooldown** (see [Pacing](#pacing-and-tiktoks-protections)): the message says until when, and names the file to delete if you must |
| 130 | Interrupted with Ctrl+C — the manifest is saved, run again to resume |

### Web UI

`dramafetch serve --cookies cookies.txt` starts a single-page UI on `http://127.0.0.1:8765/` — stdlib `http.server`, vanilla JS, no CDN, a phone-sized layout, your light/dark preference — that works like a paste-a-link downloader (SnapAny-style), in three steps:

1. Paste the series URL (any episode of it, or the bare series id) → **Resolve**. The episode list appears with each episode's cover, length and `free` / `locked` badge (locked ones are unticked and show their hints). Resolving runs inside the request and takes 10–40 s while Chromium opens TikTok; the page says so while it waits. The list is then kept on the server for 15 minutes — resolving the same series twice within that time costs nothing (the status line says when the list was fetched), and the download step reuses it — and a small **Refresh list** link next to the title fetches it again.
2. **Download all free** — one click — or tick episodes and **Download selected**; the list resolved a moment ago is reused, so this is no second visit to TikTok. Jobs run one at a time (more are queued) and are paced exactly like the CLI: `serve` takes the same pacing, engine, naming and cover flags as `download` (`--pace`, `--rest-every`, `--engine`, `--name-format`, `--thumbnail`, …). The files land on the computer running DramaFetch, under `--out`: `<Series name> [<series id>]/<Series name> - Episode NN.mp4`, its cover embedded in the video by default — `--thumbnail both` or `file` saves the cover as an image next to the video as well, or instead (see [File names and thumbnails](#file-names-and-thumbnails)).
3. Watch the progress table (polled every 2 s). Every row this job downloaded (status `done`) gets a **Save video** link and, when a cover is available — embedded in the video or saved next to it — a **Cover** link: they copy the file (the embedded cover as a `.jpg` / `.png`) from the server to the device you are browsing from — a phone or a TV, for instance. Episodes an earlier run already saved show up as `skipped-exists`, without links (delete the file on the server, or start `serve` with `--overwrite`, to download them again). The files themselves stay on the server; the page says where.

**After a refusal.** When TikTok has refused a request — HTTP 403, HTTP 429 or a captcha, met by the CLI or by a job of this server — DramaFetch does not contact TikTok again for 30 minutes (the cooldown described in [Pacing](#pacing-and-tiktoks-protections)), and the web UI honours it like the CLI: **Download** answers `429` with the cooldown message — when TikTok refused, until when, and which file to delete to lift it early — and the page disables the download buttons and counts the minutes down (locally; nothing polls TikTok or the server for it). **Resolve** still shows a list fetched less than 15 minutes ago, because that involves no request, but a fresh list has to wait too. A job that was already queued behind the one that met the refusal ends as `error` with the same message instead of knocking again.

**From a phone or TV on your home network.** The server binds to `127.0.0.1` by default, so only the computer it runs on can reach it. To use the page from another device on the same Wi-Fi, bind to every interface with an access token — `dramafetch serve --host 0.0.0.0 --token <long random string> --cookies cookies.txt` — then open `http://<pc-ip>:8765/` on that device and enter the token once: the page shows a small **Access token** form the first time an API call is refused, and a session cookie (`HttpOnly`, `SameSite=Strict`, 30 days; nothing in the page's own storage) remembers it. `DRAMAFETCH_TOKEN=…` in the environment works too (the flag wins). The token must be at least 8 characters of visible ASCII without spaces or quotes, and a `--host` other than loopback (`127.0.0.1`, `::1`, `localhost`) without a token is a usage error (exit 2) before anything is bound; the startup line says `token: set` or `token: none (loopback only)`, never the value. The token guards every `/api/*` route — resolving, downloading, job status, files, doctor — while the page itself is public; your TikTok cookies never leave the server either way. It is plain HTTP for your own LAN, not for the internet: nothing is encrypted. As before, the output directory is fixed by `--out` (the page cannot choose paths), every POST must be `Content-Type: application/json`, and only requests whose `Host` header names the bound host or localhost are answered — bound to every interface (`0.0.0.0` / `::`) the server cannot know its own addresses, so there it accepts any IP address but still no other host name: reach the page by IP, `http://<pc-ip>:8765/`, as above (a name such as `mypc.local` gets a 403).

JSON API, for scripts (with a token, send `Authorization: Bearer <token>` or the cookie): `POST /api/session {"token"}` → `204` + `Set-Cookie: dramafetch_session=…` (`401` when wrong; needs no token itself); `POST /api/resolve {"url", "refresh"?: true}` → the series and its episodes, each with its `cover_url`, plus `from_cache` (the list was resolved less than 15 minutes ago and reused — the server keeps the 32 most recently resolved series, never a failed resolve) and `resolved_at` (when it was fetched, seconds since the epoch); `"refresh": true` fetches the list again; `POST /api/download {"url", "episodes": "1-5" | null, "include_locked": bool}` → `202 {"job_id"}` (it reuses a cached list too); `GET /api/jobs/<id>` → `{state: queued|running|done|error, results: [{number, title, status, message, path, file_name, thumbnail}], …}` (`thumbnail` means a cover is available for that row — embedded in the video or saved as a file next to it — and is settled once, when the row is recorded, not at every poll); `GET /api/files/<job id>/<number>` → the finished video of that row as an `attachment` (`Content-Type` from the suffix, `Content-Length`, `Content-Disposition` with `filename` and `filename*`, streamed in 64 KiB chunks) and `GET /api/files/<job id>/<number>/cover` → its cover: the `<same name>.jpg|.jpeg|.png|.webp` file next to the video when there is one, otherwise the cover embedded in the video, sent from memory as `image/jpeg` or `image/png` with its `Content-Length` and a `Content-Disposition` naming `<video name>.jpg|.png` — both only for `done` rows whose path resolves inside `--out` (never a `.part`; the video is opened only after that check); anything else is `404 {"error": "no such file"}`; `GET /api/doctor`. Bodies are capped at 64 KiB; errors are `{"error", "kind", "hint"?}` with a 4xx/5xx status (401 with `kind: "auth"` for a missing token, with `LoginRequiredError` for a TikTok login; 429 with `kind: "cooldown"` and a `Retry-After` header in seconds while TikTok is not to be contacted after a refusal — from `/api/download` always and from `/api/resolve` unless the list is cached — and 429 with `RateLimitedError` for a rate limit met while resolving; 502 discovery failed; 503 captcha).

### Why not a public site (SnapAny-style)?

A hosted "paste a link, get the file" site would have to do four things this tool deliberately does not. It would hold visitors' TikTok cookies — the key to their accounts — on a third-party server, because TikTok serves the episode list only to a logged-in session. It would call TikTok from a datacenter address, which is exactly what TikTok's protection targets, and one busy address would be rate-limited or banned for every visitor at once. It would relay every episode through that server — gigabytes per series, for every visitor. And it would carry the Terms-of-Service and takedown exposure of redistributing the studios' videos. DramaFetch instead runs where the session and a home IP already are, your own computer, and the web UI simply lets the other screens in your house use it.

## Troubleshooting

| Symptom | Likely cause → what to do |
| --- | --- |
| `No video formats found` (status `failed-unavailable`) | Not logged in, the episode is locked, or it is not available in your region → check that `info` says `free`, refresh `cookies.txt`; `--include-locked` only confirms that a locked episode fails |
| Discovery ends on `/login`, exit 3 | TikTok wants a session → export `cookies.txt` from the logged-in browser and pass `--cookies`; cookies also expire, export again |
| HTTP 429 / `failed-rate-limited`, exit 5 | Too many requests → wait 30–60 min (the tool enforces the first 30: see the next row), then run the same command to resume; raise the pauses (`--delay-min 8 --delay-max 20`, `--rest-every 5`) or use `--pace human`; never run two instances |
| HTTP 403 / `failed-blocked` ("blocked (HTTP 403): TikTok refused the request; wait 30-60 minutes before trying again"), exit 5 | TikTok's protection refused the request (volume, or a session it does not accept) → wait 30–60 min (the first 30 are enforced: see the next row), then resume with the same command; raise the pauses, use `--pace human`, try `--engine browser` (about half the requests); if it keeps happening, export a fresh `cookies.txt`; never run two instances |
| `error: TikTok refused a request at HH:MM (…); DramaFetch waits until HH:MM (N min left) before contacting TikTok again — delete … to lift it, at your own risk`, exit 5 (also `✗ cooldown: …` in `doctor`, a 429 in the web UI) | The 30-minute cooldown after a 403 / 429 / captcha: nothing contacted TikTok → wait until the time shown and run the same command (the manifest resumes). There is no flag to skip it; deleting the file the message names lifts it, which is how a session that TikTok already distrusts gets blocked for good |
| `download looks incomplete or wrong: <reason> (kept as … (incomplete).mp4)`, status `failed`, exit 2 | The saved video failed the [integrity check](#file-names-and-thumbnails) — `not a valid MP4`, `truncated MP4 (… atom cut short …)` or `truncated body` (the transfer stopped early), `no audio track`, `duration 20 s, expected 120 s` (a short preview instead of the episode: locked for your account, or TikTok served the wrong rendition) → run the same command again (the episode is retried, the quarantined file is left alone); if the same episode keeps failing, check that `info` says `free` and look at the `(incomplete)` file; `--no-verify` keeps such files as they come, for debugging only |
| `no playable stream: locked, region-restricted or not logged in (…)` (status `failed-unavailable`, `--engine browser`) | The play URLs the episode list — and then a fresh list — offered were refused (403/404/410) or were not videos (at most 4 are requested per episode) → the episode is locked or region-restricted, or the session is not logged in: check that `info` says `free`, refresh `cookies.txt`; with `--include-locked` this is the expected outcome for a locked episode |
| `; cover: could not embed (mutagen is not installed: pip install mutagen); file kept` (or `; saved as file`) in `dramafetch.json` or the web UI row of a `done` episode | mutagen, the library that writes the cover into the MP4, is not installed in this environment → `pip install mutagen` (it comes with `pip install -e .`; `dramafetch doctor` has a `mutagen` line); the cover was kept as a file next to the video, nothing is lost |
| `; cover: could not embed (…); file kept` with another reason, in `dramafetch.json` or the web UI row of a `done` episode | The downloaded file is not an MP4 mutagen can write to (`MP4StreamInfoError`; a `.webm` / `.mkv`), or the write failed (disk full) → the video is untouched and the cover sits next to it as a file; `--thumbnail file` skips the attempt altogether |
| `; cover: webp cannot be embedded; file kept` (or `; saved as file`) in `dramafetch.json` or the web UI row of a `done` episode | TikTok served that cover as WEBP (its `dynamicCover`), which the MP4 `covr` atom cannot hold → the cover is kept as `<name>.webp`; nothing to fix |
| `could not start the browser: …` (status `failed`, `--engine browser`) | The download engine could not launch Chromium → `playwright install chromium`, or pass `--browser-channel chrome` / `--browser-path PATH` (the flags discovery uses); the message repeats for each episode until the run stops after 3 failures in a row |
| `stopped: 3 consecutive failures (last: …)`, exit 2 | Three episodes failed in a row, so the run stopped before it started to look like hammering → read the last message (login? unavailable?), fix the cause, run again to resume; `--max-consecutive-failures 0` disables the stop |
| `cookies file … has malformed lines (line N: …)`, status `failed` | A line of `cookies.txt` is not seven tab-separated fields (or has a non-numeric expiry); yt-dlp would print it, value included → delete or fix that line, or export the file again |
| Captcha / "Verify to continue", exit 4 (while listing) or `failed-blocked`, exit 5 (`--engine browser` met it while refreshing the list) | TikTok's bot check → run with `--headful`, solve it in the window, retry; the manifest resumes the run |
| `Unsupported URL` from plain `yt-dlp` | yt-dlp does not know `/shortdrama/` pages (yt-dlp/yt-dlp#17725) — that is why this tool exists; use `dramafetch download` |
| "no episode list within N s" | The page did not load the list → `--timeout 90`, `--headful` to watch, `--strategy browser`; then `--dump-raw raw/` and open an issue with the files |
| Episodes missing / "gap" warning | TikTok paginated differently or hides locked items → `info` prints the warnings; `--dump-raw` shows what the API returned |
| Short link `vm.tiktok.com/…` rejected | Short links are not resolved → open it in the browser and paste the full `/shortdrama/episode/` address |

## Limitations

- No paywall, DRM or entitlement bypass, ever: locked episodes are listed and skipped (or tried and failed with `--include-locked`).
- Short links (`vm.tiktok.com`, `vt.tiktok.com`, `tiktok.com/t/…`) are not expanded.
- TikTok changes its web app without notice, and the field names that mark an episode as locked are heuristics (`catalog.lock_hints`). When something breaks, `info --dump-raw raw/` saves the raw payloads to adjust the parsers against.
- Built without network access to TikTok: the fixtures mirror payloads observed in October 2026 and the integration test drives a real Chromium against a fake TikTok. The first real run is the real test.
- No parallel downloads, by design; the pacing defaults are a floor to raise for long series — the flags do accept lower values (the tests against the fake server need them), but nothing below the defaults is safe against TikTok (see [Pacing](#pacing-and-tiktoks-protections)).

## Development

```bash
cd DramaFetch && . .venv/bin/activate
ruff check . && ruff format --check . && mypy && pytest   # the definition of done
pytest -m integration                                      # a real Chromium against tests/integration/fake_tiktok.py
PYTHONPATH=src python -m dramafetch doctor                 # run the CLI from the checkout without installing
```

`pytest -m integration` runs only when `DRAMAFETCH_CHROMIUM` points at a Chromium binary or `/opt/pw-browsers/chromium` exists (the cloud sandbox); after `playwright install chromium`, export it the way CI does: `DRAMAFETCH_CHROMIUM="$(python -c 'from playwright.sync_api import sync_playwright; p = sync_playwright().start(); print(p.chromium.executable_path); p.stop()')"`. Without it the browser tests are skipped, not passed. CI runs all of this in the `dramafetch` job of [`../.github/workflows/ci.yml`](../.github/workflows/ci.yml). Rules for agents and the module map: [`CLAUDE.md`](./CLAUDE.md).

`DRAMAFETCH_STATE_DIR` relocates DramaFetch's state directory — today just `cooldown.json`, the file behind the 30-minute cooldown (default `~/.dramafetch`); every test runs with it pointed at a temporary directory (the autouse fixture in `tests/conftest.py`), so no test, unit or integration, ever touches your real cooldown. The fake TikTok server has two switches for the integrity check, `truncate_media` (the CDN announces the whole file and stops at 60 %) and `short_media` (the list keeps the fixtures' 92-second durations while the CDN serves the 3-second fixture); the lists it serves otherwise say `duration: 3`, what its media really lasts.

Hidden flags on `info`, `download` and `serve`, for tests and diagnostics (not in `--help`): `--base-url URL` points discovery (and, with `--engine browser`, the download engine's refresh of expired play URLs) at another host such as the fake TikTok server, `--page-count N` (default 30) and `--max-pages N` (default 60) bound the `item_list` pagination, `--page-delay S` (default 0.8) is the minimum pause between pages (the pause actually taken is 1–2 times that, randomised). To drive the CLI against the fake server from a checkout: start `tests/integration/fake_tiktok.py`'s `FakeTikTok` in a Python shell, then `PYTHONPATH=src python -m dramafetch info 7699393770256782354 --strategy browser --base-url http://127.0.0.1:<port> --browser-path /opt/pw-browsers/chromium --page-count 10`.

Layout: `src/dramafetch/` — `urls` (parse what is pasted), `discovery/` (browser, static, cookies), `catalog` (pure parsing of TikTok payloads), `manifest` (resumable runs), `downloader` (yt-dlp), `downloader_browser` (the browser engine), `media` (the integrity check of a saved video and the `(incomplete)` quarantine), `cooldown` (the 30-minute "do not contact TikTok" file), `thumbnails` (the cover: sniffing, the sidecar, embedding into the MP4 through mutagen, reading it back), `engine` (the seam shared by both front ends: pacing, early stops, the cooldown recording, `make_downloader`), `cli`, `web/` (stdlib server, job queue, `static/index.html`). Tests live in `tests/`, payload fixtures in `tests/fixtures/`, the fake TikTok server in `tests/integration/`.
