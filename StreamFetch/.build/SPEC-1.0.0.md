# StreamFetch for Chrome — specification of version 1.0.0

Date: 2026-11-08. Repository: `/home/user/projects` (branch `claude/wonderful-meitner-k32mix`). New top-level project folder: `StreamFetch/`. Written by the coordinator for parallel implementers; every rule here is binding unless it contradicts `AGENTS.md` / the root `CLAUDE.md` (which win). Everything in English: code, comments, docs, commit; the UI ships in English and Spanish (`_locales`). No model identifiers anywhere in the repository.

## 1. What it is

A Manifest V3 Chrome extension (Windows first, installed with **Load unpacked**) that downloads videos from **Dailymotion** and **Bilibili** into standard MP4 files, the way the owner uses SnapAny today but reliably: paste several links at once, see each video detected with its title, duration and the best quality the user's own browser session can play, download them one after the other with polite pacing, and get a JSON report of anything that did not download. Sibling of `DramaFetch/extension/` (same engineering rules, same quality bar, same legal posture); it shares no code with it (copy and adapt patterns, never import across projects).

The owner's acceptance criteria (verbatim intent, Spanish → English): "a first version of very high quality, where I can paste several links at once, that downloads the files well, in high quality and correctly, with safety measures against blocks, with the option to download a JSON in case of failures" and "that reads Dailymotion and Bilibili links, detects the online videos well, and downloads them well: audio, duration and video".

## 2. The line (scope, legal posture) — binding

- StreamFetch downloads only what the user's OWN logged-in Chrome session can already play on the two sites, for personal offline viewing. The legal notice (section 12) ships verbatim in the README, the app footer and both locales (a test compares them).
- Never: bypass DRM, paywalls, geo-restrictions, age gates, logins or any access control; never decrypt (an `EXT-X-KEY` with a METHOD other than `NONE`, or `pssh` / `encv` / `enca` boxes in an MP4, is refused and never saved); never compute, forge or replay the sites' request signatures or risk-control parameters; never spoof fingerprints or user agents; never use proxies, VPN tricks or IP rotation; never patch or inject into the sites' pages. The extension reads the page or JSON the site serves to the user's browser and fetches the media URLs that document offers to that session, with the browser's own cookies and headers. The ONLY header changes are on its own media requests: `Referer` set to the site's origin and `Origin` removed — exactly what the sites' own players send — through one declarativeNetRequest session rule whose initiator is the extension itself (copy the pattern of `DramaFetch/extension/src/app/downloader.js` `refererRule` / `applyRefererRule`).
- Be polite by design (section 7): one video at a time, one media request at a time, jittered pauses, bounded retries with backoff, a full stop and a 30-minute cooldown after the site refuses (429, 412, a 403 on a page or manifest, a login or verification wall). Never parallelise, never add a way to skip the cooldown or go below the pacing floors.
- Privacy: never read, log, store or export cookie values, tokens or `Authorization` headers; the report strips query strings from every URL it lists (signed URLs) and never contains request headers.

## 3. Facts from primary sources (yt-dlp 2026.10.26 extractors, read 2026-11-08 — the sandbox cannot reach either site; the owner verifies on a real machine)

### Dailymotion
- Video ids: `x` + lowercase alphanumerics (e.g. `x8vu47w`), also `k…` ids (e.g. `k2Y4Mjp7krAF9iCuINM`). Pages: `https://www.dailymotion.com/video/<id>[_slug]`, `https://dai.ly/<id>`, `https://www.dailymotion.com/embed/video/<id>`, `https://geo.dailymotion.com/player[/xxxxx].html?video=<id>`; a `?playlist=<xid>` suffix names a playlist (refused in 1.0, see section 4).
- Player metadata: `GET https://www.dailymotion.com/player/metadata/video/<id>?app=com.dailymotion.neon` (JSON). Fields used: `title`, `duration` (seconds), `owner.screenname`, `owner.id`, `created_time`, `explicit`, `posters` / `thumbnails` ({height: url}), `qualities` — a dict quality → list of `{type, url}`; the HLS master is the entry with `type == "application/x-mpegURL"` under `qualities.auto`; entries with `type == "application/vnd.lumberjack.manifest"` are ignored; other types are direct files (not expected today). `error` when the video cannot be played: `{code, title, raw_message}`; `DM007` = geo-blocked (the message names it); any other code → unavailable with the site's title. The request carries the user's cookies (family filter `ff`, login), so what the JSON offers is what the session may play.
- The HLS master lists variants (`#EXT-X-STREAM-INF` with `BANDWIDTH`, `RESOLUTION`, `CODECS`, `FRAME-RATE` sometimes, `NAME="1080"` …); media playlists list segments; the segment container may be MPEG-TS or fMP4 (`#EXT-X-MAP`) — support both. Dailymotion's CDN answers manifest requests from non-browser clients with an error (yt-dlp issue #15526): from the user's Chrome the request is a browser's request and needs nothing special. Live streams (`isOnAir`) are out of scope: a media playlist without `#EXT-X-ENDLIST` is refused as live.
- Hosts seen in the extractor and tests: `www.dailymotion.com`, `geo.dailymotion.com`, `dai.ly`, `s1.dmcdn.net` / `s2.dmcdn.net` (posters); manifests and segments live under `*.dailymotion.com` and `*.dmcdn.net` (host permissions cover both wildcards; a URL outside them is never requested and the row says so).

### Bilibili
- Video ids: `BV` + 10 alphanumerics (`BV1GJ411x7h7`) or `av` + digits. Pages: `https://www.bilibili.com/video/<id>[/]?p=<part>`; short links `https://b23.tv/<code>` redirect to the page (follow the redirect, keep only a `bilibili.com` target). Festival pages (`/festival/...?bvid=`), bangumi (`/bangumi/play/ep…|ss…`), cheese, space, lists, audio: refused in 1.0 with a clear message.
- The video page HTML embeds `window.__INITIAL_STATE__ = {...};` and `window.__playinfo__ = {...}` (JSON objects; extract them with a brace-matching scanner that understands strings and escapes, the way yt-dlp's `_search_json` does — never `eval`). `__INITIAL_STATE__.videoData`: `bvid`, `aid`, `title`, `desc`, `pic`, `duration`, `pages[]` (`cid`, `page`, `part`, `duration`), `rights.is_stein_gate` (interactive video → refused), `is_upower_exclusive` (supporter-only: refused when no DASH is served; when DASH exists but `accept_description` contains `试看`, the served stream is a trial clip → refused, never saved as the video). `__INITIAL_STATE__.error.trueCode`: `-403` → login required; `-404` → deleted or geo-restricted. A page without `__INITIAL_STATE__` but with `window._riskdata_` carrying `v_voucher` → the site is rate-limiting this session → stop + cooldown. `upData.name` / `mid` = uploader.
- `__playinfo__.data` is the playurl answer the page requested with `fnval=4048` for the part shown (`?p=N`; the first part without `p`): `dash.video[]` with `id` (quality: 127 8K, 126 Dolby Vision, 125 HDR, 120 4K, 116 1080p60, 112 1080p+, 80 1080p, 64 720p, 32 480p, 16 360p), `codecs` (`avc1.…`, `hev1.…`, `av01.…`), `codecid`, `bandwidth`, `width`, `height`, `frameRate`, `baseUrl` / `base_url`, `backupUrl` / `backup_url` (lists), `mimeType`, `size`; `dash.audio[]` with `id` (30216 64k, 30232 132k, 30280 192k), `codecs` (`mp4a.40.2`), `bandwidth`, `baseUrl`, `backupUrl`; `dash.dolby.audio[]` (`ec-3`, premium) and `dash.flac.audio` (premium); `support_formats[]` (`quality`, `new_description`, `display_desc`, `codecs[]`) and `accept_quality[]` describe what exists, which may exceed what this session is served (premium-only qualities are simply absent from `dash.video` — never requested, the row's hint names them: "1080P60 needs a premium membership"); `timelength` (ms). A `durl` answer (legacy FLV/MP4 segments, no `dash`) is refused in 1.0 ("legacy stream, not supported yet"). Each m4s URL is a complete fragmented MP4 file of one track (`ftyp`/`styp`, `moov` with one `trak`, `sidx`, many `moof`+`mdat`), served with `Range` support; its query carries a `deadline` (expiry) — a 403 on it means expired or refused: re-read the page once and continue.
- The CDN requires `Referer: https://www.bilibili.com/` (a 403 without it) and answers 412 when it bans a client (`Request is blocked by server (412)`), 429 when rate-limiting. Hosts: `*.bilivideo.com` (`upos-sz-mirror*.bilivideo.com`), `*.bilivideo.cn` (`*.mcdn.bilivideo.cn` is a P2P-ish mirror: use `baseUrl` first, backups in order), `upos-hz-mirrorakam.akamaized.net`, covers on `*.hdslb.com`.
- Multi-part videos ("anthology", `pages.length > 1`): one page fetch per part (`?p=N`), paced like any page request; `?p=N` in the pasted link selects that part only; a bare link means all parts.

## 4. Inputs (`lib/urls.js`)

`parseInput(text) → { items: Item[], refused: Refused[], dropped: string[] }` over the batch textarea (one link per line; `#` comments, blank lines, text after whitespace + `#` ignored; duplicates dropped by canonical key; max 100 items).

```
Item = { key: string, site: "dailymotion" | "bilibili", kind: "video",
         id: string,            // Dailymotion xid; Bilibili bvid or "av<digits>"
         part: number | null,   // Bilibili ?p=N, else null
         shortLink: string | null, // "https://b23.tv/<code>" or "https://dai.ly/<id>" when pasted so
         pageUrl: string,       // canonical https://www.dailymotion.com/video/<id> or https://www.bilibili.com/video/<id>[?p=N]
         original: string }
Refused = { original: string, reason: "playlist" | "bangumi" | "space" | "list" | "audio" | "live" | "other-site" | "unsupported-path" | "junk" }
```
Canonical key: `dailymotion:<id>` / `bilibili:<bvid or av…>:<part or all>`. A `b23.tv` link's id is unknown until resolved: `id = "b23:<code>"`, resolved by the resolver (then re-keyed and de-duplicated against the batch).

Statuses of a target (`lib/messages.js`): `queued`, `resolving`, `downloading`, `finishing`, `verifying`, `done`, `skipped-exists`, `failed`, `failed-unavailable` (the site refuses it for this session: geo, login, premium, deleted, DRM, live, unsupported stream), `failed-rate-limited` (429 / 412 → stop + cooldown), `failed-blocked` (403 on a page or manifest, a verification wall → stop + cooldown), `stopped` (the run stopped before it). Failures carry `{ code, params }` where `code` is one of a fixed list (`http_status`, `host_not_covered`, `redirect_refused`, `no_response`, `truncated_body`, `not_a_video`, `encrypted`, `key_protected`, `live_stream`, `discontinuous_stream`, `legacy_stream`, `geo_blocked`, `login_required`, `premium_only`, `supporter_only`, `trial_only`, `deleted`, `interactive`, `rate_limited`, `blocked`, `verify_failed`, `remux_failed`, `save_failed`, `stopped`, `unsupported_link`, `no_streams`, `cooldown`) and `messages.render(code, params) → string` gives the English text (used by the report and by the English UI); the Spanish UI renders the same code through `_locales` (`i18n.js` `renderFailure`), with the same parameters.

### The common sample model (shared by `ts.js`, `mp4.js`, `remux.js`)
```js
/** One elementary-stream sample, codec-agnostic. `dts`/`cts` in the track's timescale; `data` names where its bytes
 *  live: a byte range of a work file (`{ file, offset, size }`) — the original fragmented m4s/fMP4 file for DASH and
 *  fMP4 HLS, or the `<key>.video.bin` / `<key>.audio.bin` sample files the TS path writes. */
/** @typedef {{ dts: number, cts: number, size: number, sync: boolean, data: { file: string, offset: number } }} SampleRef */
/** @typedef {{ kind: "video"|"audio", timescale: number, stsd: Uint8Array, width: number|null, height: number|null,
 *   sampleRate: number|null, channelCount: number|null, language: string, samples: SampleRef[] }} TrackPlan */
```
A `TrackPlan` is what the progressive writer needs and nothing more: the sample entry box (`stsd`, built or copied), the timescale and the ordered samples. Sources: `mp4.collectFmp4` (DASH m4s, fMP4 HLS) and `ts.TsDemuxer` (TS HLS).

### `lib/ts.js` — the MPEG-TS demuxer (ours; H.264 video + AAC audio, what Dailymotion's TS HLS carries)
```js
export class TsDemuxer {
  /** @param {{ onSample: (kind: "video"|"audio", sample: { dts: number, cts: number, sync: boolean, bytes: Uint8Array }) => void,
   *            onTrack: (kind, info: { timescale, stsd: Uint8Array, width, height, sampleRate, channelCount }) => void,
   *            onProblem: (code: "unsupported_codec"|"corrupt_stream", params: object) => void }} hooks */
  constructor(hooks)
  push(chunk: Uint8Array): void   // any chunking: 188-byte packets re-aligned across pushes (sync byte 0x47; resync on loss)
  flush(): void                   // emits the last access unit / frames
}
```
Rules: PAT → PMT PID; PMT → elementary PIDs by stream type: `0x1B` H.264 (video), `0x0F` AAC ADTS (audio); `0x24` HEVC, `0x03/0x04` MP3, `0x81` AC-3 and anything else → `onProblem("unsupported_codec", {streamType})` and the download fails with that code (1.0 supports what Dailymotion serves). PES reassembly per PID (payload_unit_start_indicator; PES length 0 for video), PTS/DTS 33-bit at 90 kHz with wrap-around unwrapping (a backwards jump larger than 2^32 ticks adds 2^33); `dts = pts` when DTS is absent. Video: Annex B start codes (3 or 4 bytes) → NAL units; an access unit ends at the next AUD (type 9) or at a VCL NAL (1–5) whose `first_mb_in_slice == 0` when a VCL NAL was already seen; SPS (7) / PPS (8) collected → `avcC` (configurationVersion 1, profile/compat/level from the SPS, `lengthSizeMinusOne` 3, the SPS/PPS lists) → `avc1` sample entry with width/height parsed from the SPS (exp-Golomb, cropping, `frame_mbs_only_flag`); AUD (9) and filler (12) NALs dropped, everything else kept, each NAL re-written with a 4-byte length prefix; `sync` = the access unit holds an IDR (5); `cts = pts − dts` (≥ 0). Audio: ADTS frames (sync `0xFFF`, 7/9-byte header, CRC skipped), possibly spanning PES packets → one sample per frame, `timescale = sampleRate`, `dts` from the PES PTS of the frame that starts a PES payload and `+1024` per following frame (a PTS jump of more than 1.5 frames resets the clock to the PES value), `cts = 0`, `sync = true`; `esds` with an `AudioSpecificConfig` (`audioObjectType = profile + 1`, `samplingFrequencyIndex`, `channelConfiguration`) → `mp4a` sample entry (channelcount, 16 bits, sampleRate 16.16). `onTrack` fires once per kind as soon as its first sample is complete; the demuxer never throws on junk (`onProblem("corrupt_stream", …)` once, then it keeps resyncing). Tests: the ffmpeg TS fixture (section 9) demuxed, every video sample's NALs re-serialised as Annex B must equal the source's (`ffmpeg -c:v copy -bsf:v h264_mp4toannexb -f h264`), the AAC frames concatenated with ADTS headers must decode framemd5-equal to the source audio, and the full pipeline (TS → `remux.js`) gives a progressive MP4 framemd5-equal to `src.mp4` on both streams.

### `lib/mp4.js` (pure, bytes in / bytes out; Uint8Array everywhere; DataView big-endian)
Box reader: `readBoxes(bytes, start, end) → {type, size, headerSize, start, end}[]` (largesize, `uuid`, size 0 = to end); `findBox(bytes, path)`; writers `box(type, ...payloads)`, `fullBox(type, version, flags, payload)`, `u32/u64/u16/u8/str4`. Parsers: `parseInit(bytes) → { tracks: TrackInfo[], movieTimescale }` with `TrackInfo = { id, kind: "video"|"audio"|"other", timescale, durationTs, handler, stsd: Uint8Array (the whole box), sampleEntryType: string, width, height, sampleRate, channelCount, language, trex: {defaultSampleDescriptionIndex, defaultSampleDuration, defaultSampleSize, defaultSampleFlags}|null, encrypted: boolean }` (`encv`/`enca`/`pssh` anywhere → `encrypted`, mirrored in `drmProblem(bytes) → string|null` which never throws); `parseFragments(bytes, fileOffset) → Fragment[]` over a buffer holding `moof`+`mdat` pairs (`fileOffset` = where the buffer starts in the file, so data references are absolute): each `Fragment = { trackId, baseDecodeTime (tfdt, BigInt→Number when safe), samples: {size, duration, flags, cts}[], dataStart, dataEnd }` resolving `tfhd` flags (base-data-offset, sample-description-index, default duration/size/flags, duration-is-empty, default-base-is-moof) and `trun` flags (data-offset, first-sample-flags, per-sample duration/size/flags/cts v0 unsigned / v1 signed); `collectFmp4(file: { name, size, slice(start, end): Promise<Uint8Array> }) → Promise<TrackPlan[]>` streams through a fragmented file in bounded windows (never the whole file in memory), builds one `TrackPlan` per track (the `stsd` copied from `moov`, `dts` from `tfdt` plus the running sum of durations, `cts` from the trun offsets, `sync` from the sample flags, data references into the same file) and skips `styp`, `sidx`, `free`, `mfra`, `emsg`; `probe(file) → { tracks: { kind, codec, timescale, durationS, sampleCount }[], durationS, progressive: boolean (moov before mdat and no moof), encrypted }` for a finished file (reads only the needed boxes); `isSyncSample(flags)`.

```js
export function planMoov(tracks, opts) → { moov: Uint8Array, mdatOffset: number, order: ChunkPlan[] }   // exported for tests
```
Rules: one video and at most one audio track, ids 1 (video) then 2 (audio); `mvhd` timescale 1000 and duration = the longest track's; per track `tkhd` (flags 3; width/height 16.16 for video, volume 0x0100 for audio), `mdhd` (the track's timescale, language), `hdlr` (`vide`/`soun`), `minf` with `vmhd` or `smhd`, `dinf`/`dref` (self-contained url), `stbl`: the `stsd` from the plan byte for byte, `stts` run-length over sample durations (duration = next dts − dts; the last sample repeats the previous duration), `stss` for video from `sync` (omitted when every sample is sync), `ctts` version 0 with every composition offset made non-negative by one shift per track (shift = −min(cts) when negative) and an `elst` (version 0, one entry: `media_time` = that shift in the media timescale, `segment_duration` = the track duration in movie timescale) whenever the shift is non-zero or the track starts later than the earliest track (an empty edit of the gap first — A/V sync is kept), `stsc`/`stsz`/`stco` (or `co64` once any chunk offset is ≥ 2^32); one `mdat` with the 64-bit largesize header when its payload exceeds 4 GiB (the header size is decided before writing: payload = the sum of all sample sizes); interleaving by `chunkS` (default 1 s) in decode order (the video chunk then the audio chunk of the same second, each chunk's samples contiguous; the last partial chunks too); `read` is called in file order, chunk by chunk, so a source file is read sequentially. The function returns the exact byte count written; `mp4.probe` of the result must say progressive with the expected tracks and durations (the downloader checks that before saving). Tests (section 9): DASH pair → one MP4 framemd5-equal to the source on both streams; fMP4 HLS → same; TS via `ts.js` → same; durations within 0.05 s of `ffprobe`'s for the source; a 3-track input and an audio-only input are refused with clear errors; chunk offsets and `stsc` runs cross-checked against `ffprobe -show_packets` positions for the first chunks.

### `app/resolver.js`
`resolve(item, ctx) → Target[] | ResolveFailure` with `ctx = { fetch, settings, bases, pause, log }`: Dailymotion → one `GET` of the metadata JSON (`credentials: "include"`), parse, then the HLS master (one GET), choose variant + audio rendition, then the media playlist(s) (one GET each) → one `Target` with `streams.kind === "hls"` (the `HlsMedia` kept in `target.raw.media`); Bilibili → `b23.tv` followed (`redirect: "follow"`, the final `response.url` must be a `bilibili.com/video/` page, else `redirect_refused`), the page `GET` (credentials included) → `parsePage` → parts (all, or the one `?p=`); for every further part one more page GET (`?p=N`) paced by `PAGE_PAUSE_S`; `chooseStreams` per part → one `Target` per part with `streams.kind === "dash"`. ### `app/downloader.js`
`download(target, ctx) → Result` with `Result = { status, failure: {code, params}|null, path: string|null, bytes: number, durationS: number|null, attempts: Attempt[], verify: {...}|null }`:
1. `applyRefererRule(site)` (DNR session rule: initiator = this extension; `requestDomains` = the site's media domains from the manifest; `Referer` set to `https://www.dailymotion.com/` or `https://www.bilibili.com/`, `Origin` removed) — in test mode the condition is a `urlFilter` on the test base.
2. `hls`: segments in order, one request at a time (`fetch`, `credentials: "include"`, `redirect: "follow"` — the final `response.url` host must be covered, else `redirect_refused`), each paced by `MEDIA_PAUSE_MS`, retried `MAX_RETRIES` times on network error / 5xx / stall (backoff), a 403/404/410 on a segment → one in-run refresh (re-fetch master + media playlist, map by segment index) then continue; a second one → `failed` (`http_status`); `ts` segments are pushed into one `TsDemuxer` per download; every emitted sample's bytes are appended to OPFS `work/<key>.video.bin` / `work/<key>.audio.bin` and its `SampleRef` recorded (two `TrackPlan`s grow in memory: a one-hour video is about a hundred thousand small records); `fmp4` segments (init first) are appended as served to `work/<key>.hls.m4s` and read back with `mp4.collectFmp4`; the first bytes of the first segment/init pass `mp4.drmProblem` (fMP4) — TS with `keyProtected` is refused BEFORE any media request (`key_protected`); `endList === false` → `live_stream` before any request; `discontinuities > 0` → `discontinuous_stream` before any request.
3. `dash`: the video file then the audio file, each one streaming GET (`response.body` reader → OPFS `work/<key>.video.m4s` / `.audio.m4s`), stall-guarded, a cut transfer resumed with `Range: bytes=<received>-` up to `MAX_RETRIES` times on the same URL (206 expected; a 200 restarts the file), then the next URL of `urls` from the start; 403 → refresh the page once (new URLs), then continue from the received offset; the init (`moov`) of each file checked with `mp4.drmProblem` as soon as it is complete (abort + `encrypted` if any).
4. Finishing (status `finishing`): the `TrackPlan`s — from the demuxer (TS), from `mp4.collectFmp4` over `work/<key>.hls.m4s` (fMP4 HLS) or over `work/<key>.video.m4s` + `work/<key>.audio.m4s` (DASH) — go through `remux.writeProgressiveMp4` into OPFS `work/<key>.final.mp4`; then `verifying`: `mp4.probe` of the final file → progressive, a video track and an audio track (unless the source offered no audio at all — then the row's message says `no audio in the source`), duration within `max(3 s, 5 %)` of `target.durationS` (when known) — a mismatch is `verify_failed` with `duration <a> s, expected <e> s` and the file is NOT saved; the browser's own decoder check (an offscreen `<video preload="metadata">` with a blob URL, 10 s timeout) is informational: a readable `duration` is recorded in `verify.browser_duration_s`, a failure to read it only appends ` (the browser could not read the file's duration: <codec>)` to a done row's message.
5. Saving: `chrome.downloads.download({ url: URL.createObjectURL(await finalHandle.getFile()), filename: targetPath, conflictAction: "uniquify", saveAs: false })`, wait for the download to complete (`chrome.downloads.onChanged` or polling `search`), then delete the OPFS work files (also on failure). A writer failure (it throws, or `mp4.probe` of its output disagrees with the plan) → `remux_failed`, nothing saved, the work files deleted; the row's message carries the writer's reason. A fragmented fallback file is NOT saved in 1.0 (the owner asked for correct files; an unfinished one would pass for the video).
6. `skipped-exists`: before any request, `chrome.downloads.search({ filenameRegex })` + `exists` check for the target path (as DramaFetch's `DownloadsView`); a file already there is skipped without a request.
Every step records `Attempt`s; `traceOf(target)` returns them for the report.

## 7. Pacing, retries, cooldown — the "safety against blocks" the owner asked for

Being blocked is prevented by behaving like one person watching, not by evasion: one request at a time; `MEDIA_PAUSE_MS` between media requests, `PAGE_PAUSE_S` between page requests, `VIDEO_PAUSE_S` between videos; at most `MAX_RETRIES` with exponential backoff per request; a stall timeout; a 429 or 412 anywhere, a 403 on a page or manifest, a verification or login wall → the run stops at once and a 30-minute cooldown starts (`cooldown` in storage, a banner, every start refused with the minutes left; the user may delete it in Settings — "at your own risk" wording — but no code path skips it). Expired media URLs (403 on a segment or m4s) → one refresh per video, never a loop. Never two videos at once; never two segments at once. Document the floors in the README.

## 8. The report (`StreamFetch/reports/…json`)
Saved automatically at the end of every run with at least one `failed*` or `stopped` row when the `report` setting is on (default), and on **Save the report**. Content per section 6 `lib/report.js`. Privacy rules there are binding. The README tells the user the report holds the sites' metadata as served (titles, ids, hosts) and asks them to read it before sharing it.

# Addendum A (2026-11-08, after the owner's message "Haz que funcione como SnapAny. https://snapany.com/bilibili-tv") — binding for 1.0.0

SnapAny's page is its **Bilibili.tv** downloader. Bilibili.tv (Bstation, also `biliintl.com`) is Bilibili's INTERNATIONAL site, a different service from `www.bilibili.com`, with its own pages, API and CDN. The owner, in Latin America, almost certainly pastes bilibili.tv links. StreamFetch 1.0.0 therefore supports THREE sources: Dailymotion, Bilibili.tv and Bilibili (mainland), and its UI follows SnapAny's flow: paste → every video appears as a card/row with its cover, title, duration and a quality selector → download. Everything below extends the spec; where it conflicts with the main text, the addendum wins.

## A.1 Facts: bilibili.tv (yt-dlp 2026.10.26, `BiliIntlBaseIE` / `BiliIntlIE` / `BiliIntlSeriesIE`, read 2026-11-08; the sandbox cannot reach the site)
- Pages (an optional two-letter language segment, any case, e.g. `/en/`, `/es/`, `/id/`): user videos `https://www.bilibili.tv/<lang>/video/<aid>` (`aid` = digits), licensed series episodes `https://www.bilibili.tv/<lang>/play/<season_id>/<ep_id>`, a whole series `https://www.bilibili.tv/<lang>/play/<season_id>` or `/media/<season_id>`; `www.biliintl.com` and bare `bilibili.tv` are the same site. Both ids are plain digits.
- Streams: `GET https://api.bilibili.tv/intl/gateway/web/playurl?platform=web&aid=<aid>` (user videos) or `…&ep_id=<ep_id>` (episodes), with the user's cookies (`credentials: "include"`) and `Referer: https://www.bilibili.tv/`. Answer `{code, message, data: {playurl: {video: [{video_resource: {url, codecs, width, height, bandwidth, size, mime_type, quality}, stream_info: {quality, desc_words}}], audio_resource: [{url, codecs, bandwidth, size, mime_type, quality}]}}}`: video-only files and audio-only files, like Bilibili's DASH, each a complete MP4 (fragmented or not — handle BOTH, see A.3). `code` 0 = ok; `10004001` → `geo_blocked`; `10004004`, `10004005`, `10023006` → `login_required` (the message says it may also be a premium-only episode: "log in to Bilibili.tv in this browser; a premium episode stays unavailable"); any other non-zero code → `failed-unavailable` with `params.site_message` = `message`. An entry without `url` is skipped; no video entry at all → `no_streams`.
- Metadata: the page HTML embeds `window.__INITIAL_DATA__ = {...}` or `window.__INITIAL_STATE__ = {...}` (Bstation layout), or Nuxt state (`__initialState`); the video object is at `OgvVideo.epDetail` (episodes), `UgcVideo.videoData` or `ugc.archive` (user videos): `title_display` / `title`, `desc`, `cover`, `formatted_pub_date`; read a duration from any of `duration`, `duration_ms`, `video_duration` when present (seconds or milliseconds by magnitude), else null. Fallbacks: the `<meta property="og:title">` and `og:image`, the `bstar-meta__title` element's text, JSON-LD `VideoObject` (`name`, `duration` ISO 8601, `thumbnailUrl`). Series: `GET https://api.bilibili.tv/intl/gateway/web/v2/ogv/play/episodes?season_id=<id>&platform=web` → `data.sections[].episodes[]` (`episode_id`, `title_display`, `title`, `cover`, a duration field when present) and `…/web/v2/ogv/play/season_info?season_id=<id>&platform=web` → `data.season.title`. Episode titles look like `E3 - Episode title`.
- Hosts: `www.bilibili.tv`, `api.bilibili.tv`, `*.biliintl.com`, covers on `*.bstarstatic.com` (`p.bstarstatic.com`, `pic.bstarstatic.com`); the media CDN hosts are NOT known from the extractor — expected under `*.bilivideo.com`, `*.bilivideo.cn`, `*.akamaized.net` (`upos-bstar1-mirrorakam.akamaized.net`) or `*.bstarstatic.com`; the manifest lists `https://*.bilibili.tv/*`, `https://*.biliintl.com/*`, `https://*.bstarstatic.com/*`, `https://upos-bstar1-mirrorakam.akamaized.net/*` next to the Bilibili ones, and a media URL on any other host is `host_not_covered` — the row and the report name the host, so the owner's first real run tells us what to add (README: "if a download says host not covered, send the report").

## A.2 Inputs (`lib/urls.js`)
`Item.site` gains `"bilibilitv"`; `Item.kind` gains `"series"` (a bilibili.tv `/play/<season_id>` or `/media/<season_id>` link: resolved into one target per episode, in order; the batch cap counts the link as one item but a series may add up to 200 targets). Ids: `aid` → `id = "<aid>"`, `kind: "video"`; episode → `id = "<ep_id>"`, `seasonId = "<season_id>"`, `kind: "episode"`; series → `id = "<season_id>"`, `kind: "series"`. Canonical keys `bilibilitv:video:<aid>`, `bilibilitv:episode:<ep_id>`, `bilibilitv:series:<season_id>`. `biliintl.com` links are canonicalised to `https://www.bilibili.tv/en/…`.

## A.4 The SnapAny-like page (group D2; the e2e tests of E2 use these ids)
Each resolved row shows: a cover thumbnail (`img.cover`, lazy — loaded only when the row is in view, one request at a time, never during a job, like DramaFetch's `CoverLoader`; a broken or missing cover shows a neutral placeholder, never an error), the title (`.title`, a link to the page URL opening in a new tab), the site badge (`.site`: `Dailymotion` / `Bilibili.tv` / `Bilibili`), the duration (`.duration`, `mm:ss` / `h:mm:ss`), a quality selector (`select.quality-select` inside `.quality`, one `<option value="<index>">` per available video stream, labelled `1080p · avc1 · 2.3 MB/s` style (`<height>p`, the codec family, the bandwidth in Mbit/s with one decimal; for HLS `<height>p` and the codecs), the pre-selected option being the global policy's choice; a premium-only quality the session cannot get appears as a disabled option `1080P60 — premium only` so the user sees what exists), the status badge, the progress cell and the message. Changing the selector before the download changes that row's `streams.variant`/`video` (and re-picks the audio by the same rules). **Download all** uses each row's current selection. A series link shows one row per episode under a group header row (`tr.group[data-group]` with the series title and `N episodes`). The summary line counts `N videos · M detected · K failed`. Keyboard: Enter in the textarea does not start anything; **Analyze** does.

## A.7 The owner's example links (2026-11-08) — binding
The owner's own examples are two bilibili.tv user videos ("UGC"): `https://www.bilibili.tv/en/video/<aid>` with a 16-digit aid, and the same with `?bstar_from=bstar-web.ugc-video-detail.related-recommend.all` (a tracking parameter the site adds to links clicked in its "related" list). Rules:
- Every query parameter and every fragment of a bilibili.tv link is ignored: none selects anything (`bstar_from`, `spm_id_from`, `share_source`, `share_medium`, `from_spmid`, `t`, …).
- The aid (and `ep_id`, `season_id`) is a STRING end to end: 16 digits today, close to 2^53 − 1; never `Number()`, `parseInt` or arithmetic, compared as strings, sent to the playurl API as text. An id read back from an API JSON answer as a number is never trusted over the URL's string (a number above 2^53 − 1 loses digits in `JSON.parse`).
- The language segment (`en`, `es`, `id`, `th`, `vi`, `zh`, any case) is optional and does not change the item key (`bilibilitv:video:<aid>`): the same video pasted with `/en/` and `/es/` is one item (the second one `dropped` as a duplicate). `bilibili.tv/video/<aid>` without `www` and without a language, and `http://`, are accepted; the canonical page is `https://www.bilibili.tv/en/video/<aid>`.
- Tests use INVENTED aids of the same shape (16 digits, e.g. `4801520000000001`) and the exact `bstar_from` value above — never the owner's real ids: the repository is public, and what the owner watches stays private.
- Any other bilibili.tv path (`/en/space/…`, `/en/trending`, a search, the home page) is refused with `unsupported-path`. Short share links (`bili.im/…`) are not in yt-dlp's extractor and are not supported in 1.0: refused with `unsupported-path` and the message to paste the full `bilibili.tv/…/video/…` link from the browser's address bar.
- The e2e batch scenario pastes, among its links, a bilibili.tv video link WITH the `bstar_from` parameter and the same video with another language segment, and asserts one row, one download.

## A.8 Dailymotion links, the owner's example (2026-11-08) — binding (the integrator makes sure of it)
The owner's example is a plain Dailymotion video page, `https://www.dailymotion.com/video/<xid>` with a 7-character xid (`x` + 6 lowercase alphanumerics). Phase 1's `urls.js` already turns it, `dai.ly/<xid>`, `/embed/video/<xid>` and the `<xid>_<slug>` form into one item `dailymotion:<xid>` (checked by the coordinator). One rule changes from the main text (section 3 and 4): a VIDEO link that also carries `?playlist=<pid>` (Dailymotion adds it when a video is opened from a playlist) is the video — the playlist parameter is ignored and the row's hint says `playlist ignored: only this video is downloaded` (both locales) — instead of being refused; only a link that names a playlist and no video (`/playlist/<pid>`, `geo.dailymotion.com/player…?playlist=<pid>` without `video=`) is refused as `playlist`. Every other query parameter of a Dailymotion link is ignored too. Tests use INVENTED xids of the same shape (e.g. `xbq9z2k`), never the owner's. The e2e batch scenario includes a Dailymotion video link with a `?playlist=` parameter and asserts that the video downloads.
